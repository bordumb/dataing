# Implement maistro branch sub-workflow execution

## Overview

The maistro workflow engine has a stub implementation for branching. When a step returns `Signal.BRANCH`, the `Runner._run_branch` method just returns the branch data unchanged instead of actually running a sub-workflow. This breaks the investigation workflow which relies on branching to test multiple hypotheses in parallel.

## Scope

**In scope:**
- Implement `_run_branch` to execute sub-workflows starting at `BranchRequest.child_start_step`
- Pass `BranchSpec.data` as `input_data` to the first branch step (not context merge)
- Run branch steps to completion (COMPLETE/FAIL signal or end of steps)
- Return context using existing `{"_full_context": context}` encoding for non-dict types
- Handle branch failures gracefully with structured error payloads
- Maintain deterministic replay (branch events in canonical order by branch name)
- Fix `_execute_step` to use `BranchRequest.merge_step` correctly
- Add investigation-specific merge strategy in dataing

**Out of scope:**
- Nested branching (branches that themselves branch) - EXPLICIT FAIL if attempted
- Branch-level AWAIT_USER - EXPLICIT FAIL if a branch step returns AWAIT_USER
- Child event logs (deferred - BranchCompleted sufficient for now)
- Distributed branch execution (all branches run in same process)

## Prerequisite Fix: merge_step Derivation

**Location**: `maistro/src/maistro/runner.py:358-366`

**Bug**: Current branching ignores `BranchRequest.merge_step` and derives `merge_step` from `StepResult.next_step`. For `GenerateHypothesesStep`, this causes the parent to resume at wrong step.

**Fix**: In `_execute_step`, when `signal == Signal.BRANCH`:
```python
merge_step = result.branch_request.merge_step  # Use BranchRequest's merge_step
# Ignore StepResult.next_step for BRANCH signal
```

**Test**: Assert emitted `BranchesRequested.merge_step` matches `BranchRequest.merge_step`.

## Approach

### 1. BranchSpec.data as input_data (NOT context merge)

**Key insight**: Investigation branch payload is designed as `input_data`, not context fields.
- `GenerateHypothesesStep` uses `data={"hypothesis": ...}`
- `GenerateQueryStep` reads `input_data["hypothesis"]`
- `InvestigationContext` doesn't have a `hypothesis` field

**Implementation**:
- `BranchSpec.data` is **deep copied** then passed as `input_data` to the **first branch step only**
- This prevents step mutations from leaking back into the frozen `BranchSpec`
- Context is forked (deep copied) from parent, unchanged
- Subsequent branch steps receive `None` for `input_data` (per normal flow)

### 2. Context Forking (Deep Copy for Isolation)

Branches need true isolation - shallow copy allows mutation leakage:

```python
def _deep_copy_context(self, context: ContextT) -> ContextT:
    import copy
    return copy.deepcopy(context)  # Works with all types
```

**Note**: Use `copy.deepcopy` uniformly (not JSON round-trip) to avoid failing on non-JSON values (UUID/datetime).

### 3. Signature Change for _run_branch

**Old**: `_run_branch(state, branch_name, branch_data) -> dict[str, Any]`
**New**: `_run_branch(state, branch_name, branch_spec, child_start_step) -> dict[str, Any]`

Parameters:
- `branch_spec` - full `BranchSpec` (for `data` and `name`)
- `child_start_step` - from `BranchRequest.child_start_step` (NOT added to `BranchSpec` to preserve schema stability)

**When `child_start_step` is None**: Use `step_order[0]` as the default start step.
Runner only has access to `engine._step_order`, not the workflow's `is_start` metadata.

**Guard for empty `step_order`**: If `step_order` is empty when `child_start_step` is None, return structured error `{"maistro": {"branch_error": {"reason": "NO_STEPS_REGISTERED", ...}}}`.

**Note**: This means branch default start may differ from workflow's `is_start=True` step.
Update `BranchRequest` docs to define default as "first step in step_order" for clarity.

**Call site update**: `_execute_branches` passes `branch_request.child_start_step` separately.

### 4. Termination Conditions

Branch runs until one of:
- Step returns `Signal.COMPLETE` → branch complete, return context
- Step returns `Signal.FAIL` → branch failed, return structured error
- Step returns `Signal.AWAIT_USER` → FAIL with structured error (reason="AWAIT_USER")
- Step returns `Signal.BRANCH` → FAIL with structured error (reason="NESTED_BRANCH")
- **next_step resolution**: Mirror Engine logic - `next_step = result.next_step or engine._default_next(current_step)`. Only complete when resolved next_step is `None`.
- `next_step` not found in step registry → FAIL with structured error
- `max_iterations` exceeded → FAIL with structured error

Invalid `child_start_step`:
- If `child_start_step` not in registry → FAIL with structured error

### 5. Result Handling (Use Existing Encoding)

Use existing `{"_full_context": context}` pattern for non-dict types:
- Branch returns `context_update` dict
- For dict contexts: return the **delta** (new/changed keys only, not full context)
- For non-dict contexts (Pydantic, dataclass): return `{"_full_context": context}`
- This matches existing `StepCompleted` encoding in `maistro/src/maistro/runner.py`
- `BranchCompleted.context_update` stays typed as `dict[str, Any]`

**Dict context delta computation** (single source of truth):
```python
def _compute_delta(initial_context: dict, final_context: dict) -> dict:
    """Return only new/changed keys from initial to final."""
    delta = {}
    for k, v in final_context.items():
        if k not in initial_context or initial_context[k] != v:
            delta[k] = v
    return delta
```

**Delta computation rule**:
- Delta = `final_branch_context - initial_forked_context`
- Computed ONCE at branch completion (not from step-level context_updates)
- This ignores intermediate step outputs; only the final state matters
- Step-level context_updates are still applied during branch execution, but the returned delta is computed from the initial fork

**Merge strategy requirements**:
- **Dict contexts**: DefaultMergeStrategy does key-level last-write-wins merge
  - Fine for simple key/value changes
  - **Limitation**: List/counter fields become "whole value changed" - last branch wins
  - Any workflow with list appends, counter sums, or nontrivial aggregation needs a custom MergeStrategy
- **Non-dict contexts**: DefaultMergeStrategy returns `branch_contexts` dict (existing behavior, unchanged)
  - This is rarely useful - non-dict workflows should provide custom merge strategy

**Update DefaultMergeStrategy** to:
1. For dict parent only: unwrap `_full_context` from each branch payload, then merge branch deltas
2. For non-dict parent: return `branch_contexts` dict unchanged (existing behavior, no unwrapping)
   - This preserves backward compatibility with existing tests
   - Non-dict workflows should use custom merge strategies for proper handling

### 6. Merge Strategy (Investigation-Specific)

**DefaultMergeStrategy updated** (§5) to unwrap `_full_context` for dict parents only.

**Add InvestigationMergeStrategy** in `dataing/src/dataing/core/investigation/flow.py`:
```python
class InvestigationMergeStrategy(MergeStrategy[InvestigationContext]):
    def merge(
        self,
        parent: InvestigationContext,
        branch_contexts: dict[str, Any],
    ) -> InvestigationContext:
        # 1. Unwrap _full_context from each branch
        # 2. Detect error payloads (maistro.branch_error key)
        # 3. Extract deltas from successful branches
        # 4. Merge into parent context
```

**Unwrapping logic** (required before delta extraction):
```python
def _unwrap_branch(payload: dict[str, Any]) -> InvestigationContext | None:
    """Returns context or None if error payload."""
    if isinstance(payload, dict):
        if "maistro" in payload and "branch_error" in payload["maistro"]:
            return None  # Error payload
        if "_full_context" in payload:
            return payload["_full_context"]
    return payload  # Direct context (shouldn't happen but handle gracefully)
```

**Field-level merge semantics (delta-based to avoid double-counting)**:

Branch contexts start from parent state, so we must compute deltas:

| Field | Merge Rule |
|-------|-----------|
| `evidence` | `new_items = branch.evidence[len(parent.evidence):]` (guard: skip if branch < parent) |
| `total_queries_executed` | `delta = max(0, branch.total - parent.total)` then sum deltas |
| `hypotheses` | Preserve from parent (branches don't modify) |
| `current_hypothesis` | Preserve from parent |
| Other fields | Preserve from parent |

**Error handling in merge**:
- Failed branches detected by `maistro.branch_error` key in payload
- Failed branches DO NOT contribute to `evidence` or `total_queries_executed`
- Error info is logged but NOT stored in context (use existing fields only)
- Merge continues even if all branches fail (SynthesizeStep handles this gracefully)

**Wire it up**: In `build_investigation_workflow()`, pass custom merge strategy.

### 7. Error Handling

Structured, namespaced error payloads:
```python
{
    "maistro": {
        "branch_error": {
            "branch_name": str,
            "step_id": str | None,
            "reason": str,  # EXCEPTION, SIGNAL_FAIL, AWAIT_USER, NESTED_BRANCH, MAX_ITERATIONS, STEP_NOT_FOUND
            "exception_class": str | None,
            "message": str,
        }
    }
}
```
- `SIGNAL_FAIL` for `Signal.FAIL` from step
- `EXCEPTION` for thrown exceptions
- Branch failures emit `BranchCompleted` with error payload - parent continues

### 8. Deterministic Ordering

Canonical order: **alphabetical sort by branch name** (stable, predictable)

**Execution model: Sequential (no concurrency)**

Run branches in a simple for-loop, sorted by name:
```python
sorted_branches = sorted(branch_request.branches, key=lambda s: s.name)
results = {}
for spec in sorted_branches:
    emit(BranchStarted(spec.name, ...))
    results[spec.name] = await self._run_branch(state, spec.name, spec, child_start_step)
    emit(BranchCompleted(spec.name, results[spec.name]))
```

**Why not concurrent?**
- `asyncio.gather` with ordered await still allows nondeterministic side effects (shared resources, global caches)
- Sequential is simpler, fully deterministic, and sufficient for now
- Concurrent can be added later with explicit reentrancy requirements

**Event order**: BranchStarted(A) → BranchCompleted(A) → BranchStarted(B) → BranchCompleted(B) → ...

### 9. Max Iterations

- `_run_branch` accepts `max_branch_iterations` parameter (default: 100)
- Branch loop counts iterations and fails if exceeded
- Test verifies deterministic failure on infinite loop

## Risks & Dependencies

- **Risk**: Branch execution could cause infinite loops if steps don't terminate
  - Mitigation: `max_branch_iterations` parameter with deterministic failure

- **Risk**: Context isolation - branches might mutate shared state
  - Mitigation: Deep copy with `copy.deepcopy`

- **Risk**: Step reentrancy with concurrent execution
  - Mitigation: Sequential execution only (no concurrency). See §8.

- **Dependency**: Existing Engine/Runner architecture must be preserved
- **Dependency**: DefaultMergeStrategy updated to unwrap `_full_context`; investigation adds custom strategy

- **Known Limitation**: Branch checkpointing
  - `run_with_checkpointing()` ignores `BranchCompleted` events
  - Branch outputs are not checkpointed until merge step completes
  - A shutdown between branch completion and merge loses branch progress
  - Acceptable for now: branches are fast; merge is the checkpoint boundary
