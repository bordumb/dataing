# Epic: Evidence Integrity and Reproducibility

## Overview

Every investigation produces a tamper-evident, reproducible audit trail via SHA-256 hash-linked evidence chains. This satisfies F500 compliance requirements and enables reproducing investigations months later. No competitor has verifiable evidence chains.

## Scope

**In Scope:**
- Fix the existing `compute_content_hash()` to use RFC 8785 canonical serialization (replacing non-deterministic `json.dumps(default=str)`)
- Include chain metadata (seq, kind, prev_hash) in hash computation for authenticated ordering
- Add `verify_chain()` pure function for chain integrity validation
- Bridge Temporal investigation workflow evidence to the hash chain system
- Add `root_hash` column to investigations table
- Add `GET /investigations/{id}/verify` API endpoint
- Add `dataing verify <investigation_id>` CLI command
- Enhance evidence export with per-item chain metadata

**Out of Scope (deferred):**
- HMAC-SHA256 with per-tenant keys (future security enhancement)
- External anchoring (RFC 3161 timestamp authorities, blockchain)
- Merkle tree batching for evidence groups
- Per-investigation opt-in (currently env-var global)

## Architecture

### Current State (Two Evidence Systems)
1. **Temporal investigation pipeline** (`core/domain_types.py:138-159`): Produces `dict[str, Any]` evidence. No hash chain. This is the primary production code path.
2. **SDK evidence system** (`core/evidence.py`, `sdk_repository.py:375-543`, `sdk_evidence` table): Rich evidence schema with `prev_hash`, `content_hash`, `seq` fields. Hash chain infrastructure exists but is disconnected from Temporal.

### Target State
- After parallel hypothesis evaluation completes in the Temporal workflow, a finalization step:
  1. Collects all evidence items
  2. Sorts them deterministically (by hypothesis_id, then by creation order within each hypothesis)
  3. Assigns sequential `seq` numbers
  4. Computes hash chain using RFC 8785 canonicalization with domain-separated SHA-256
  5. Persists to `sdk_evidence` table
  6. Sets `root_hash` on the investigation record
- Verification endpoint loads evidence, recomputes hashes, validates chain linkage

### Key Design Decisions
1. **Chain post-completion** (not real-time): Hash chain is built in a finalization step after parallel hypothesis evaluation. This preserves the parallel execution model while ensuring deterministic ordering.
2. **RFC 8785 for canonicalization**: Replaces `json.dumps(sort_keys=True, default=str)` which is non-deterministic across Python versions/platforms.
3. **Domain-separated hashing**: `sha256(b"evidence_v1:" + canonical_bytes)` to prevent second preimage attacks.
4. **Hash covers chain metadata**: `content_hash = sha256(canonical({seq, kind, prev_hash, content}))` — not just content alone. This authenticates ordering and linkage.
5. **INSERT-only evidence**: Remove `ON CONFLICT DO UPDATE` from `store_evidence()` to prevent silent overwrites.
6. **Pre-feature investigations**: Verify endpoint returns "chain not available" (distinct from "chain broken") for investigations without evidence chain.

## Acceptance Criteria

- [ ] Each evidence item has `content_hash` (SHA-256 of canonicalized content + chain metadata)
- [ ] Each evidence item has `prev_hash` (content_hash of previous item)
- [ ] First item has `prev_hash = null`
- [ ] Investigation has `root_hash` (content_hash of final evidence item)
- [ ] `GET /investigations/{id}/verify` validates chain integrity
- [ ] Broken chain detected and reported with specific item seq number
- [ ] Chain includes: hypotheses, queries, results, synthesis
- [ ] Export includes per-item chain metadata for external verification
- [ ] `dataing verify <investigation_id>` CLI command works
- [ ] Pre-feature investigations return "chain not available" (not "broken")
- [ ] Hash computation is deterministic across Python 3.11+ versions
