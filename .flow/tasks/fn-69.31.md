# fn-69.31 [M1] Adapter-specific credential schemas and auth isolation

## Description
### Goal
Each principal connects with **its own** credentials, and nothing else (D11; design §5.2, §17). This fixes a Critical flaw: today's gateway merge (`adapters/datasource/gateway.py:218-224`) keeps base authentication, such as BigQuery's `credentials_json` (`sql/bigquery.py:165`), so a user's credential row can run as the datasource's service account.

### Implementation
- **For each `SourceType`, declare:**
  - which datasource config fields are **authentication material**, e.g. user, password, private_key, credentials_json, token;
  - a **credential payload schema**, e.g. username/password (+ role/warehouse), a Snowflake key pair (+ passphrase), BigQuery service-account JSON, or a token.
- **`build_connection_config(base_config, credential)`:**
  - Strips **all** auth fields from the base config.
  - Injects only the principal's credential.
  - Rejects incomplete credentials before connecting.
- **Use the schemas everywhere:**
  - saving and testing user credentials (`routes/credentials.py:42` only accepts username/password today);
  - automation credentials (fn-69.14);
  - `CredentialsService` decryption (`core/credentials.py:74` requires username/password);
  - the gateway (fn-69.6).
- **Stored credentials:** migrate the stored payloads to JSON that follows the schema.
## Acceptance
- [ ] BigQuery: the base config holds a privileged `credentials_json`, and the principal's credential doesn't have one → execution **fails** and never uses the base account.
- [ ] Save, test and run round-trip for username/password, a Snowflake key pair and BigQuery JSON.
- [ ] Incomplete credentials are rejected with a clear error, and existing username/password rows still work after the migration.
