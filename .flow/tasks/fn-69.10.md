# fn-69.10 [M1] CLI: dataing checks commands

## Description
### Goal
`dataing checks schema | validate | run | apply` (design §5.6, §16, §17).

### Implementation
- **Where the CLI lives:** follow fn-55's direction (the `dataing` package). Settle the console-script clash with `dataing-cli` first. Never ship two scripts.
- **`run <path> --datasource-config <file> [--as-of]` runs locally, with local implementations of fn-69.8's ports:**
  - specs come from files;
  - the catalog comes from adapter introspection;
  - queries go straight to the adapter (fn-69.32), under `InProcessLimiter`;
  - history is local (`.dataing/history.sqlite`, configurable).

  It exits 1 on `fail` or `error`, and never contacts the API, Postgres or Redis.
- **Datasource config format:** `type`, connection fields, and credentials only as `${ENV}` references.
- **`run --remote <suite>`** calls the automation endpoint (fn-69.9) with a key issued by `POST /checks/automation-keys`, and uses the same exit codes.
- **`apply <path> --source <name>` enforces deployment order:**
  1. Read the source's `applied_sha` and `revision` (fn-69.9).
  2. Check locally that `git merge-base --is-ancestor <applied_sha> HEAD` holds. If it doesn't, **refuse**: this is a stale or out-of-order CI job. `--force` overrides with a warning.
  3. Apply HEAD with `expected_revision` (compare-and-swap).

  If `applied_sha` isn't in the local history (a shallow clone), fail with instructions to fetch more history.
- **`validate`** runs locally with file:line errors. **`schema`** writes out the JSON Schema.
- **Command pattern:** follow `dataing_cli/commands/git.py:15-89`.
## Acceptance
- [ ] `validate` prints 1-based errors and exits non-zero.
- [ ] `run` against a DuckDB fixture works with the network disabled, and baselines carry across two separate processes.
- [ ] Deployment order: an old CI job whose SHA is an ancestor of `applied_sha` is refused, even though it read the latest revision; a fast-forward apply succeeds; a shallow clone gives a clear error.
- [ ] Contract test against a real API (`-m integration`): issue an automation key, then `run --remote` creates a trigger=`api` run with the automation identity; there's a 409 without an automation credential, and a 403 with an ordinary key.
- [ ] The monorepo has exactly one `dataing` console script.
