# fn-68.3 Stop uv.lock drift: refresh lock, --frozen hooks, --locked CI, re-lock on release

## Description
The mypy pre-commit hook ran `uv run mypy`, which re-locked and rewrote uv.lock. The lock still recorded the workspace packages at 1.17.0 while pyproject said 1.20.0.

Refresh the lock in its own commit and stop hooks and CI from rewriting it. Fix the release version bump and Dependabot so that pyproject changes also update uv.lock.
## Acceptance
- uv.lock refreshed in its own commit (editable versions 1.17.0 -> 1.20.0)
- mypy hook uses `uv run --frozen` (never rewrites uv.lock)
- CI installs with `uv sync --locked` so a stale lock fails fast
- Release pipeline re-locks after bumping versions so drift does not recur


## Done summary
- uv.lock refreshed in its own commit: only the four editable workspace versions moved 1.17.0 -> 1.20.0.
- Root cause: semantic-release bumps pyproject versions without re-locking, and Dependabot's "pip" ecosystem bumps pyproject without touching uv.lock.
- .releaserc.json prepareCmd now runs `uv lock` and commits uv.lock; release.yml installs uv.
- dependabot.yml Python ecosystem switched to "uv".
- ci-backend.yml uses `uv sync --locked` (both jobs); mypy hook uses `uv run --frozen --extra dev`.
- Verified: cold-cache release replay changes only version fields; stale lock -> `uv sync --locked` fails, `uv run --frozen` leaves lock untouched, plain `uv run` rewrites it; mypy hook passes.
