# fn-45.6 Add integration tests for SAML flow (Okta, Azure AD)

## Description

Create end-to-end integration tests that exercise the complete SAML SP-initiated flow from
discovery through ACS to JWT issuance. Since real IdP connections are not available in CI, tests
use a mock IdP that generates valid SAML responses with configurable attributes. Tests should cover
the specific response formats from Okta and Azure AD (the two primary target IdPs), including
their different attribute name conventions and group claim structures.

Depends on: fn-45.4 (JIT provisioning) and fn-45.5 (metadata + admin config).

### Implementation

1. Create a test fixture `python-packages/dataing-ee/tests/integration/sso/conftest.py`:
   - `MockSAMLIdP` class that generates signed SAML responses:
     ```python
     class MockSAMLIdP:
         """Generates SAML responses for testing."""

         def __init__(self, entity_id: str, signing_key: RSAPrivateKey, cert: Certificate):
             ...

         def build_response(
             self,
             name_id: str,
             attributes: dict[str, list[str]],
             audience: str,
             acs_url: str,
             in_response_to: str | None = None,
             not_before: datetime | None = None,
             not_on_or_after: datetime | None = None,
         ) -> str:
             """Return base64-encoded SAML response."""
     ```
   - Generate a self-signed certificate + key pair as a pytest fixture.
   - Create DB fixtures for a tenant with SAML SSO config using the test certificate.

2. Create `python-packages/dataing-ee/tests/integration/sso/test_saml_flow.py`:
   - **Test full SP-initiated flow**:
     a. POST `/auth/sso/discover` with email -> get `method="saml"`, extract `state`.
     b. Build a mock SAML response using `MockSAMLIdP`.
     c. POST `/auth/sso/saml/acs` with `SAMLResponse` + `RelayState` -> get JWT tokens.
     d. Verify JWT contains correct `user_id`, `org_id`, `role`.
   - **Test Okta-style attributes**: Okta uses `user.email`, `user.firstName`, `user.lastName`,
     group claim in a custom attribute. Verify mapping works.
   - **Test Azure AD-style attributes**: Azure AD uses
     `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress` for email,
     `http://schemas.microsoft.com/ws/2008/06/identity/claims/groups` with group OIDs. Verify
     mapping works with configured attribute mapping.
   - **Test JIT provisioning**: First login creates user + SSO identity. Second login reuses.
   - **Test existing user linking**: Create a password user, then SAML login with same email
     and verified email attribute -> links accounts.
   - **Test security: unverified email blocking**: SAML assertion without verified email attribute
     for an existing user -> 400 error.
   - **Test expired assertion**: NotOnOrAfter in the past -> 400.
   - **Test tampered assertion**: Modify assertion XML after signing -> 400 signature error.
   - **Test replayed state**: Use same RelayState twice -> 400 on second attempt.

3. Create `python-packages/dataing-ee/tests/integration/sso/test_saml_metadata.py`:
   - Verify metadata endpoint returns parseable XML.
   - Verify a mock IdP can consume the SP metadata to build a valid response.

4. Add an Okta-specific and Azure AD-specific attribute mapping fixture to test realistic
   configurations:
   ```python
   OKTA_ATTRIBUTE_MAPPING = {
       "email": "user.email",
       "name": "user.displayName",
       "given_name": "user.firstName",
       "family_name": "user.lastName",
       "groups": "groups",
   }
   AZURE_AD_ATTRIBUTE_MAPPING = {
       "email": "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress",
       "name": "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name",
       "groups": "http://schemas.microsoft.com/ws/2008/06/identity/claims/groups",
   }
   ```
