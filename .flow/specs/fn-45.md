**Plan ref:** Task 2.1.2 (SAML portion - OIDC already done in fn-6)
**Phase:** 2 (Enterprise)
**Designation:** Enterprise

## Overview

Implement SAML 2.0 Service Provider support alongside the existing OIDC implementation. Schema and types already exist (`SSOProviderType.SAML`, SAML config fields). Need the actual authentication flow implementation.

## Existing State (~30% built)

- DB schema: `sso_configurations` table has `saml_idp_metadata_url`, `saml_idp_entity_id`, `saml_certificate` columns
- Types: `SSOProviderType.SAML = "saml"` in `dataing_ee/core/sso/types.py`
- Repository: stores/retrieves SAML fields
- Feature gate: `Feature.SSO_SAML` exists
- SSO routes currently REJECT SAML: `if sso_config.provider_type != SSOProviderType.OIDC` returns "Unsupported"

- SAML login redirect flow (SP-initiated)
- SAML assertion consumer service (ACS) endpoint

- SAML metadata endpoint for IdP configuration

## Gap Analysis Risks

- **IdP-initiated flow security**: IdP-initiated SAML is vulnerable to CSRF. Consider supporting only SP-initiated, or require explicit admin opt-in for IdP-initiated.
- **Clock skew**: SAML assertions have NotBefore/NotOnOrAfter conditions. Define tolerance for clock skew between Dataing and the IdP (recommend 5 minutes). Without this, intermittent login failures occur.
- **Group-to-role mapping**: SAML group names are arbitrary strings from the IdP. Existing RBAC has roles OWNER, ADMIN, MEMBER. Need configurable per-tenant mapping from arbitrary IdP group names to these three roles.
- **Certificate rotation**: How many certificates can be active simultaneously during rotation? Admin UI should show cert expiry dates.
- **SAML assertion encryption**: Some IdPs send encrypted assertions (not just signed). Decryption support needed for strict IdPs.
- **Existing user linking**: If a user exists with email A via password auth and SAML assertion comes in with email A, auto-linking could be an account takeover risk if IdP email is not verified. Follow fn-6.6 pattern carefully.
