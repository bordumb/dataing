## TemporalInvestigationClient Contract

The client wraps Temporal operations and provides the same interface as the current queue-based approach:

```python
class TemporalInvestigationClient(Protocol):
    async def start_investigation(
        self,
        investigation_id: str,
        tenant_id: str,
        datasource_id: str,
        alert_data: dict,
    ) -> str:
        """Start workflow. Returns workflow_id.

        Uses workflow_id=investigation_id with WorkflowIDReusePolicy.REJECT_DUPLICATE.
        If AlreadyStarted, returns existing workflow_id (idempotent start).
        """

    async def cancel_investigation(self, investigation_id: str) -> None:
        """Send cancel signal to workflow."""

    async def get_status(self, investigation_id: str) -> InvestigationStatus:
        """Query workflow for current status.

        For running workflows: uses Temporal query.
        For completed/terminated workflows: falls back to investigations table.
        """

    async def send_user_input(self, investigation_id: str, payload: dict) -> None:
        """Send user input signal to resume AWAIT_USER."""
```

**Start Workflow Implementation (Idempotent)**:
```python
async def start_investigation(self, investigation_id: str, ...) -> str:
    workflow_id = investigation_id  # Use investigation_id as workflow_id

    # Investigation stays 'pending' until workflow actually starts
    # (created with status='pending' by API route)

    try:
        handle = await self.client.start_workflow(
            InvestigationWorkflow.run,
            input,
            id=workflow_id,
            task_queue=settings.TEMPORAL_TASK_QUEUE,
            id_reuse_policy=WorkflowIDReusePolicy.REJECT_DUPLICATE,
        )
        # Update to running only after successful start
        await db.execute(
            "UPDATE investigations SET status = 'running', workflow_id = $1 WHERE id = $2",
            workflow_id, investigation_id
        )
        return workflow_id
    except WorkflowAlreadyStartedError:
        # Idempotent: workflow already exists
        # Ensure DB is in sync
        await db.execute(
            "UPDATE investigations SET status = 'running', workflow_id = $1 WHERE id = $2 AND status = 'pending'",
            workflow_id, investigation_id
        )
        return workflow_id
    except Exception:
        # Transient failure - leave as pending (can retry)
        # Only the workflow itself can mark terminal failure
        raise
```

**Status transitions**:
- `pending` → `running`: After `start_workflow` succeeds (set by client)
- `running` → terminal: Only workflow activities can set terminal status via `persist_final_result`
- Transient start failures leave status as `pending` for retry

```python
# In investigation_service.py (NOT an activity)
async def create_main_branch(self, investigation_id: UUID) -> UUID:
    """Create main branch synchronously (idempotent)."""
    row = await self.db.fetch_one(
        """
        INSERT INTO investigation_branches (investigation_id, branch_type, name, status)
        VALUES ($1, 'main', 'Main Investigation', 'active')
        ON CONFLICT (investigation_id) WHERE branch_type = 'main' DO UPDATE
            SET updated_at = NOW()
        RETURNING id
        """,
        investigation_id
    )
    await self.db.execute(
        "UPDATE investigations SET main_branch_id = $1 WHERE id = $2 AND main_branch_id IS NULL",
        row["id"], investigation_id
    )
    return row["id"]
```
This ensures `get_state()` always has a valid `main_branch_id` before workflow starts.

**Reconciliation for orphaned workflows**:
If `start_workflow` succeeds but the DB update fails, we have a running workflow with `pending` status. A lightweight reconciliation job fixes this:

```python
async def reconcile_pending_investigations():
    """Run periodically to fix orphaned workflows where DB update failed after start."""
    pending = await db.fetch_all(
        """
        SELECT id FROM investigations
        WHERE status = 'pending'
          AND created_at < NOW() - INTERVAL '5 minutes'
        """
    )
    for row in pending:
        workflow_id = str(row["id"])
        try:
            handle = client.get_workflow_handle(workflow_id)
            await handle.describe()  # Throws if not found
            # Workflow exists - fix DB
            await db.execute(
                "UPDATE investigations SET status = 'running', workflow_id = $1 WHERE id = $2 AND status = 'pending'",
                workflow_id, row["id"]
            )
        except WorkflowNotFoundError:
            # No workflow - leave pending (can retry or timeout)
            pass

# Reconciliation job location: Run in Temporal worker startup loop
# Alternative: pg_cron job or FastAPI background task
```

**Job ownership**: The reconciliation job runs in the Temporal worker's startup/health loop (every 5 minutes). This ensures it only runs when workers are active and has access to the Temporal client.

```python
async def get_status(self, investigation_id: str) -> InvestigationStatus:
    workflow_id = investigation_id
    try:
        handle = self.client.get_workflow_handle(workflow_id)
        return await handle.query(InvestigationWorkflow.get_status)

            current_step="completed" if row["status"] == "completed" else row["status"],
            progress=1.0 if row["status"] == "completed" else 0.0,
            is_complete=row["status"] in ("completed", "failed", "cancelled", "timed_out", "inconclusive"),
            awaiting_user=False,
        )
```

## Activity Idempotency Strategy

Each activity that performs side effects MUST use idempotency keys with atomic claim:

```python
import hashlib

@activity.defn
async def execute_query(input: ExecuteQueryInput) -> dict:
    # Idempotency key prevents duplicate work on retry
    idempotency_key = f"{input.investigation_id}-{input.hypothesis_index}-execute"
    # Hash task token for storage (tokens can be large)
    lock_token = hashlib.sha256(activity.info().task_token).hexdigest()

    # Step 1: Check if already completed
    existing = await db.fetch_one(
        "SELECT status, result, locked_by, locked_at FROM idempotency_results WHERE idempotency_key = $1",
        idempotency_key
    )

    if existing and existing["status"] == "completed":
        return existing["result"]

    # Step 2: Try to claim (insert or update stale/failed)
    if not existing:
        # New key - insert
        await db.execute(
            """
            INSERT INTO idempotency_results (idempotency_key, investigation_id, status, locked_by, locked_at)
            VALUES ($1, $2, 'in_progress', $3, NOW())
            ON CONFLICT (idempotency_key) DO NOTHING
            """,
            idempotency_key, input.investigation_id, lock_token
        )
        # Re-check in case of race
        existing = await db.fetch_one(
            "SELECT status, result, locked_by FROM idempotency_results WHERE idempotency_key = $1",
            idempotency_key
        )
    elif existing["status"] in ("failed",) or (
        existing["status"] == "in_progress" and existing["locked_at"] < datetime.now(UTC) - timedelta(minutes=10)
    ):
        # Reclaim stale/failed key
        await db.execute(
            """
            UPDATE idempotency_results SET status = 'in_progress', locked_by = $1, locked_at = NOW()
            WHERE idempotency_key = $2 AND (status = 'failed' OR (status = 'in_progress' AND locked_at < NOW() - INTERVAL '10 minutes'))
            """,
            lock_token, idempotency_key
        )
        existing = await db.fetch_one(
            "SELECT status, result, locked_by FROM idempotency_results WHERE idempotency_key = $1",
            idempotency_key
        )

    # Step 3: Check ownership
    if existing["locked_by"] != lock_token:
        # Another attempt owns it - wait with backoff
        for attempt in range(10):
            await asyncio.sleep(min(0.5 * (2 ** attempt), 30))
            check = await db.fetch_one(
                "SELECT status, result FROM idempotency_results WHERE idempotency_key = $1",
                idempotency_key
            )
            if check["status"] == "completed":
                return check["result"]
            if check["status"] == "failed":
                break
        return await execute_query(input)  # Retry claim

    # Step 4: We own the lock - execute the actual work
    try:
        query_result = await database.execute(input.query)
        await db.execute(
            """
            UPDATE idempotency_results SET status = 'completed', result = $1, completed_at = NOW()
            WHERE idempotency_key = $2 AND locked_by = $3
            """,
            query_result, idempotency_key, lock_token
        )
        return query_result
    except Exception:
        await db.execute(
            "UPDATE idempotency_results SET status = 'failed' WHERE idempotency_key = $1 AND locked_by = $2",
            idempotency_key, lock_token
        )
        raise
```

**Key points**:
- Uses `$1`, `$2` positional params to match `AppDatabase` adapter
- Uses `fetch_one`/`execute` methods matching the adapter API
- `locked_by` uses SHA256 hash of activity task token
- Owner check on all updates prevents interference
- No transactions held during sleep

**Retry Policies**:
| Activity | Timeout | Max Attempts | Non-Retryable Errors |
|----------|---------|--------------|---------------------|
| gather_context | 5min | 3 | AuthError, NotFound |
| generate_hypotheses | 5min | 3 | RateLimitError |
| execute_query | 10min | 2 | InvalidSQLError |
| interpret_evidence | 5min | 3 | RateLimitError |
| synthesize | 5min | 3 | RateLimitError |

**Branch/Snapshot Strategy: Main + User branches (hypothesis deferred)**

- **User branch**: Created on AWAIT_USER for user input flows (keeps existing UX)
- **Hypothesis branches**: DEFERRED to Phase 2 (hypothesis evaluation happens on main branch)

```python
@activity.defn
async def persist_snapshot(input: PersistSnapshotInput) -> UUID:
    """Called at key workflow steps (idempotent via unique constraint).

    IMPORTANT: input.step_cursor MUST always contain step_index (never NULL).
    - Single-occurrence steps: step_index = 0
    - Repeated steps: step_index = hypothesis_index or iteration number
    """
    # Validate step_index is present (fail fast, never persist with NULL)
    if input.step_cursor.get("step_index") is None:
        raise ValueError("step_cursor.step_index is required for idempotency")

    # Idempotent upsert using unique constraint on (branch_id, step, temporal_run_id, step_index)
    row = await db.fetch_one(
        """
        INSERT INTO investigation_snapshots (investigation_id, branch_id, step, context, step_cursor)
        VALUES ($1, $2, $3, $4, $5)
        ON CONFLICT (branch_id, step, (step_cursor->>'temporal_run_id'), (step_cursor->>'step_index'))
        DO UPDATE SET context = $4  -- Update context on retry
        RETURNING id
        """,
        input.investigation_id, input.branch_id, input.step, input.context, input.step_cursor
    )
    snapshot_id = row["id"]
    # Update branch head to latest snapshot
    await db.execute(
        "UPDATE investigation_branches SET head_snapshot_id = $1, updated_at = NOW() WHERE id = $2",
        snapshot_id, input.branch_id
    )
    return snapshot_id

# NOTE: create_main_branch is a SERVICE METHOD (not an activity) - see "Main branch timing" section above.
# It's called from the API route BEFORE starting the workflow, not from within the workflow.

@activity.defn
async def update_branch_status(input: UpdateBranchStatusInput) -> None:
    """Update branch status (active/completed/abandoned)."""
    await db.execute(
        "UPDATE investigation_branches SET status = $1, updated_at = NOW() WHERE id = $2",
        input.status, input.branch_id
    )
```

**Workflow calls these activities** at each step to keep snapshots in sync. `InvestigationService.get_state()` and SSE continue to query snapshots/branches unchanged.

Progress and status tracked via workflow instance variables:

```python

        self._is_complete = False
        self._awaiting_user = False
        self._user_input: dict | None = None
        self._cancelled = False

    @workflow.query
    def get_status(self) -> InvestigationStatus:
        return InvestigationStatus(
            current_step=self._current_step,
            progress=self._progress,
            is_complete=self._is_complete,
            awaiting_user=self._awaiting_user,
        )
```

**AWAIT_USER Handling**:
- `wait_condition()` with 7-day timeout (configurable via `AWAIT_USER_TIMEOUT_DAYS`)
- On timeout: mark investigation as `timed_out`, not `failed`
- Signal `user_input` resumes workflow and clears `_awaiting_user`

**Status Transitions**:
| From | To | Trigger |
|------|-----|---------|
| `running` | `completed` | Workflow finishes successfully |
| `running` | `failed` | Unrecoverable activity error |
| `running` | `cancelled` | User sends cancel signal |
| `awaiting_user` | `running` | User sends input signal |
| `awaiting_user` | `timed_out` | 7-day timeout expires |

**`timed_out` vs `cancelled` semantics**:
- `cancelled`: User explicitly requested cancellation via API
- `timed_out`: AWAIT_USER deadline expired without user response
- Both are terminal states; neither is a "failure" for retry purposes

## Child Workflow Concurrency

Bounded fan-out for parallel hypothesis evaluation:

```python
MAX_CONCURRENT_HYPOTHESES = 5  # Configurable via settings

async def evaluate_hypotheses_parallel(hypotheses: list[Hypothesis]) -> list[EvidenceResult | ChildFailure]:
    """Fan-out with bounded concurrency and failure isolation.

    Note: Uses asyncio.gather with return_exceptions=True so child failures
    don't crash the parent workflow. Failed children are recorded, not re-raised.
    """
    results = []
    # Process in batches of MAX_CONCURRENT_HYPOTHESES
    for batch_start in range(0, len(hypotheses), MAX_CONCURRENT_HYPOTHESES):
        batch = hypotheses[batch_start:batch_start + MAX_CONCURRENT_HYPOTHESES]
        # Start all child workflows in batch (deterministic ordering)
        handles = []
        for i, h in enumerate(batch):
            handle = await workflow.start_child_workflow(
                EvaluateHypothesisWorkflow.run,
                EvaluateHypothesisInput(hypothesis=h, index=batch_start + i),
                id=f"{workflow.info().workflow_id}-hypothesis-{batch_start + i}",
                parent_close_policy=ParentClosePolicy.TERMINATE,
            )
            handles.append((batch_start + i, handle))

        # Await all results with return_exceptions=True (child failure won't crash parent)
        batch_results = await asyncio.gather(
            *[h.result() for _, h in handles],
            return_exceptions=True
        )

        # Process results, recording failures
        for (idx, _), result in zip(handles, batch_results):
            if isinstance(result, Exception):
                # Record failed child for synthesis (don't re-raise)
                results.append(ChildFailure(hypothesis_index=idx, error=str(result)))
            else:
                results.append(result)

    return results

@dataclass
class ChildFailure:
    """Marker for failed child workflow (included in synthesis input)."""
    hypothesis_index: int
    error: str
```

**Failure handling**: Failed child workflows are wrapped in `ChildFailure` and included in results. The synthesis activity receives all results (successes + failures) and can report which hypotheses couldn't be evaluated.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Temporal server down | Investigations blocked | Restart server; workflows replay from history |
| Determinism violations in workflow | Non-determinism errors on replay | All LLM/DB calls in activities; add replay tests |
| Activity timeout too short | Valid investigations fail | Per-activity timeouts: LLM 5min, DB query 10min |
| `bond/` package depends on maistro | Build breaks | Explicitly refactor bond in Task 10 before deleting maistro |
| Activity retry duplicates work | Corrupted counts, duplicate DB writes | Idempotency keys stored in `idempotency_results` table |
| AWAIT_USER never responds | Workflow stuck forever | 7-day timeout with `timed_out` status (not `failed`) |
| Unbounded child workflow fan-out | Worker overload | MAX_CONCURRENT_HYPOTHESES=5 with batched execution |
| Child workflows orphaned on cancel | Resource leak | ParentClosePolicy.TERMINATE on all child workflows |

## Implementation Notes

The following details are specified at architecture level and will be finalized during implementation:

1. **Idempotency pattern**: The atomic claim pattern is specified; exact SQL may need adjustment based on `AppDatabase` adapter capabilities. The key invariant is: single atomic operation determines ownership.

2. **Branch/snapshot sync**: Activities call `persist_snapshot` at key steps. Exact snapshot contents and step cursor format will match existing `InvestigationService` expectations.

3. **Legacy schema migration**: Pre-requisite task to audit and update any `AppDatabase` queries using legacy columns (`dataset_id`, `metric_name`, etc.) to use unified schema (`alert`, `outcome`).

4. **Status vocabulary**: API response layer maps new DB statuses (`pending`, `running`) to legacy API vocabulary (`queued`, `active`) for backwards compatibility.
