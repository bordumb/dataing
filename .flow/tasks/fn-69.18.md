# fn-69.18 [M2] Codify writes CheckSpec via LLM structured output; exports rebuilt

## Description
### Goal
Replace keyword matching with the LLM writing `CheckSpec` checks from **controlled input** (D8), validated and dry-run (design §7.6, §17).

### Implementation
- **Controlled Codify input.** Build a structured `CodifyInput`. Never forward free-text synthesis, evidence strings or metadata; `agents/models.py:232` asks for evidence that includes data points. It contains:
  - the dataset and its schema (column names and types);
  - the anomaly type and metric;
  - the affected columns;
  - hypothesis categories;
  - aggregate numbers from the alert;
  - the existing suite keys;
  - the JSON Schema.
- **LLM call:** a prompt in `agents/prompts/`, called with `BondAgent(output_type=PromptedOutput(...))` (pattern: `agents/client.py:68-102,304-308`).
- **Checking each proposal:**
  - Validate it (fn-69.1) and compile it (fn-69.4).
  - Dry-run it as the clicking user through a gateway session, and flag checks that would fail.
- **Key collisions:** if a key already exists in the dataset's suite, return a conflict for the UI to resolve (rename or replace).
- **Output:** a canonical YAML snippet plus the target suite path, or a new suite file.
- **Route:** update `POST /investigations/{id}/codify` (`routes/investigations.py:629`). The keyword extractors (`core/codify.py:586,743-925`) go away here. The exports are handled in fn-69.33.
## Acceptance
- [ ] Tests with recorded LLM output produce valid CheckSpec for the null_spike investigation.
- [ ] A synthesis whose text and evidence contain distinctive row values (e.g. `alice@example.com`, `ORD-99317`) produces an **outbound model request** without them, verified at the fake agent client.
- [ ] Invalid LLM output gives a clean error, not a 500.
