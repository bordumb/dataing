# GUI-First Notebook UX

## Overview

Transform the notebook experience from magic-command-first to GUI-first. Users should be able to connect, attach to assets, and run investigations entirely through the JupyterLab sidebar, with magics becoming optional power-user shortcuts.

**North Star UX**: "Open notebook → connect once → pick an asset → ask a question → watch timeline → export report."

## Scope

### In Scope
- Connection wizard in JupyterLab sidebar (replaces `%dataing connect` as default path)
- Asset typeahead picker (replaces manual `%dataing attach`)
- 409 ambiguity resolver modal (turns error into guided selection)
- Unified workspace context **scoped by workspace + kernel** (single source of truth per notebook)
- Settings persistence via ISettingRegistry
- SSE reconnection with resume capability (backend contract + UI)
- "Copy reproducible snippet" feature for collaboration
- Instrumentation for UX metrics

### Out of Scope
- Datasource creation/onboarding wizard (separate epic)
- Mobile/responsive design

## Approach

### Phase 1: Backend Prerequisites
Build the APIs and infrastructure needed before GUI work can begin:
1. **Asset search endpoint** - Cross-datasource search with defined contract (`/api/v1/asset-instances/search`)
2. **Credential handling** - 3 explicit modes: OS keyring, env var, session-only
3. **Connection test exposure** - Wire existing `/datasources/test` through server extension proxy

### Phase 2: Connection Wizard
Replace `%dataing connect` as the default connection method:
4. **Connection wizard UI** - Multi-step wizard (URL → auth mode detection → test → save)
5. **Settings persistence** - ISettingRegistry for non-secret config (URL, auto-connect, workspace_id)
6. **Magic integration** - `%dataing connect` reads saved GUI config, prints reproducible snippet

### Phase 3: Attach UX
Replace manual `%dataing attach` with GUI-driven asset selection:
7. **Asset typeahead component** - Search-based picker with debouncing and keyboard nav
8. **409 resolver modal** - When ambiguous, show datasource chooser with human names
9. **Unified workspace context** - Server extension as source of truth, keyed by (workspace_id, kernel_id), versioned commands

### Phase 4: Polish
Production-ready UX improvements:
10. **SSE reconnection** - Backend contract for `?from_seq=` + UI reconnect status
11. **Timeline improvements** - Grouped events, icons, run status indicators
12. **Keyboard shortcuts** - Quick access to common sidebar actions

## Acceptance Criteria

1. **Connection**: User can connect to backend entirely through sidebar GUI without typing any magic commands
2. **Attach**: User can search for and select assets through typeahead picker
3. **409 Handling**: Ambiguous datasource situations show a chooser modal, not an error
4. **State Sync**: Sidebar and magics always show consistent state (same attached datasource, same run status)
5. **Persistence**: Connection settings survive JupyterLab restart
6. **Backward Compatible**: Existing `%dataing` magic commands continue to work
7. **Security**: API keys are never stored in plain text in JupyterLab settings files
8. **Multi-Notebook**: Each notebook's kernel has isolated context; sidebar reflects active kernel
9. **Portability**: "Copy reproducible snippet" outputs magic commands matching current GUI state
10. **Zero Magic Required**: New user can complete connect → attach → run → export **without ever executing a magic cell**

## Status Surface Area (REQUIRED)

Every state element must be visible in consistent locations:

| Element | Sidebar | `%dataing status` | Timeline Events | Error Messages |
|---------|---------|-------------------|-----------------|----------------|
| Connection URL | Yes (pill) | Yes | — | Yes |
| Connected state | Yes (green/red) | Yes | — | Yes |
| Attached asset URN | Yes (badge) | Yes | Yes (header) | Yes |
| Resolved datasource | Yes (badge) | Yes | Yes (every event) | Yes |
| Current run status | Yes (indicator) | Yes | Yes | Yes |
| Credential mode | Yes (label) | Yes | — | — |

This kills 80% of confusion tickets.

## Architecture Decisions

### Workspace + Kernel Identity (fn-23.9)

Two-level identity for stable persistence and telemetry:

```python
@dataclass
class WorkspaceState:
    workspace_id: str        # Stable across sessions (from ISettingRegistry or generated UUID)
    kernel_id: str           # Current kernel (transient)
    state_version: int
    connection: ConnectionState
    binding: BindingState
    run: RunState
```

**Why workspace_id?**
- Enables "restore previous context" without cross-workspace pollution
- Segments telemetry correctly (same user, different projects)
- Survives kernel restarts when stored in ISettingRegistry

**Generation**:
- First launch: generate UUID, store in ISettingRegistry as `dataing:workspaceId`
- Subsequent launches: read from settings
- JupyterHub: can use workspace path if available

**State key**: `(workspace_id, kernel_id)` in server extension memory.

### Active Kernel Resolution (fn-23.9)

How the sidebar finds "active kernel":

```
Active Kernel Resolution Order
┌─────────────────────────────────────────────────────────────┐
│ 1. Active notebook panel's sessionContext.session.kernel.id │
│    └─ If notebook focused and has running kernel → use it   │
│                                                             │
│ 2. If no notebook focused OR no kernel running:             │
│    └─ Show empty state: "Select a notebook to connect"      │
│                                                             │
│ 3. [Nice-to-have] Dropdown to choose among running kernels  │
│    └─ Useful for power users with multiple notebooks        │
└─────────────────────────────────────────────────────────────┘
```

**Frontend implementation**:
```typescript
const notebookTracker = app.shell.currentWidget as NotebookPanel | null;
const kernel = notebookTracker?.sessionContext?.session?.kernel;
const kernelId = kernel?.id ?? null;

if (!kernelId) {
  // Render "Select a notebook" empty state
}
```

### State Machine (ALL transitions)

```
                    ┌─────────────────┐
                    │  DISCONNECTED   │
                    │  (initial)      │
                    └────────┬────────┘
                             │ connect()
                             ▼
                    ┌─────────────────┐
        clear() ◄───│   CONNECTED     │───► disconnect()
           │        │  (no binding)   │         │
           │        └────────┬────────┘         │
           │                 │ attach()         │
           │                 ▼                  │
           │        ┌─────────────────┐         │
           ├────────│     BOUND       │─────────┤
           │        │ (asset+ds set)  │         │
           │        └────────┬────────┘         │
           │                 │ start_run()      │
           │                 ▼                  │
           │        ┌─────────────────┐         │
           │        │    RUNNING      │─────────┤
           │        │  (run active)   │         │
           │        └───┬────────┬────┘         │
           │            │        │              │
           │     complete()   error()           │
           │            │        │              │
           │            ▼        ▼              │
           │        ┌─────────────────┐         │
           └────────│  BOUND (idle)   │◄────────┘
                    │  or ERROR       │
                    └─────────────────┘

Allowed commands per state:
┌───────────────┬──────────────────────────────────────────┐
│ State         │ Allowed Commands                         │
├───────────────┼──────────────────────────────────────────┤
│ DISCONNECTED  │ connect()                                │
│ CONNECTED     │ attach(), disconnect(), clear()          │
│ BOUND         │ start_run(), attach(), clear()           │
│ RUNNING       │ (none - wait for complete/error)         │
│ ERROR         │ start_run(), attach(), clear()           │
└───────────────┴──────────────────────────────────────────┘
```

### State Conflict Resolution (fn-23.9)

Replace "last-write-wins" with **versioned commands**:
- State changes are intentional commands: `connect()`, `attach(urn)`, `set_datasource(id)`, `start_run()`, `clear()`
- Each command returns: `{state: {...}, state_version: int}`
- Commands include `expected_version` param; server returns 409 if stale
- UI refreshes state on 409, re-applies user intent

**Idempotency for start_run()** (prevents double-click duplicates):
```python
POST /dataing/command/start_run
{
  "kernel_id": "...",
  "question": "Why did revenue drop?",
  "expected_version": 5,
  "client_request_id": "uuid-from-client"  # Required
}
```
- Server deduplicates within 60s window by `client_request_id`
- If duplicate detected, returns existing `run_id` (not error)
- Prevents accidental duplicate investigations from retries/double-clicks

### Credential Storage (fn-23.2)

Three explicit modes with wizard detection:
1. **OS Keychain** (best) - `keyring` library, auto-detected
2. **Environment Variable** - `DATAING_API_KEY`, for CI/containers
3. **Session-Only** - User pastes key, not persisted, works everywhere

Wizard shows: "Detected mode: [OS Keychain / Env Var / Session-Only]" with explanation.

**Session-Only Security Model**:
- Stored in **server extension process memory only** (not kernel, not frontend)
- Cleared on:
  - Server extension restart (JupyterLab server restart)
  - Explicit `DELETE /dataing/credentials`
- **NOT** sent back to frontend after initial connect (only `{stored: true}`)
- Never logged, even in debug mode

### SSE Resume Backend Contract (fn-23.10)

**Event Format**:
- Run events MUST have `seq` field (monotonically increasing per run)
- SSE endpoint accepts `?from_seq=123` query param
- Server extension caches `last_seq` per `(workspace_id, kernel_id, run_id)`

**Retention Policy**:
- Backend keeps last **1000 events** OR **last 30 minutes** per run (whichever is larger)
- After retention window, events are eligible for cleanup
- Clients should not assume infinite replay

**replay_unavailable Handling**:
```
event: replay_unavailable
data: {"message": "Events before seq 50 unavailable", "available_from": 50}
```

**UI behavior when replay unavailable**:
1. Show banner: "Some history unavailable"
2. Continue streaming from `available_from`
3. Offer "Open full run in web UI" link (if web UI exists)
4. Do NOT show as error (this is expected for long-running investigations)

### Asset Search API Contract (fn-23.1)

**Clarification**: This endpoint returns **asset instances** (asset + specific datasource), not abstract assets. Each result is a concrete table/view in a specific datasource.

```
GET /api/v1/asset-instances/search
  ?q=<query>           # Required, min 1 char
  &limit=<int>         # Default 10, max 100
  &cursor=<string>     # Opaque pagination cursor
  &datasource_id=<id>  # Optional filter

Response:
{
  "results": [
    {
      "asset_urn": "urn:dataing:postgres:ds_prod:public.orders",  # Includes datasource
      "display_name": "orders",
      "type": "table",
      "schema": "public",
      "datasource_id": "ds_prod",
      "datasource_name": "Production Analytics",
      "platform": "postgres",
      "match_reason": "name_prefix"
    }
  ],
  "next_cursor": "..." | null,
  "total_hint": 42
}
```

**Why "asset instances"?**
- Each result maps to exactly one datasource (no ambiguity)
- 409 only happens if user types asset name manually without selecting from picker
- Picker UX is cleaner: user sees "orders (Production)" vs "orders (Staging)" as separate options

### UI Framework (fn-23.4, fn-23.7, fn-23.8)

Pragmatic hybrid approach:
- **Lumino shell**: Sidebar container, status indicators, simple views
- **React embedded**: Typeahead picker, connection wizard steps, 409 modal
  - JupyterLab supports this pattern via `ReactWidget.create()`
  - Avoids reinventing complex a11y (keyboard nav, focus management, debouncing)

## Failure-Mode UX Checklist

For each operation, define what the UI does on failure:

### Connect
| Failure | Type | UI Response | State Preserved | Recovery |
|---------|------|-------------|-----------------|----------|
| Network unreachable | Transient | "Cannot reach server. Check URL." + Retry button | URL preserved | Click Retry or edit URL |
| Invalid API key | Permanent | "Invalid API key" + Re-enter option | URL preserved | Re-enter key |
| Server error (500) | Transient | "Server error. Try again." + Retry button | All preserved | Click Retry |

### Attach
| Failure | Type | UI Response | State Preserved | Recovery |
|---------|------|-------------|-----------------|----------|
| Asset not found | Permanent | "Asset not found" | Connection preserved | Search again |
| 409 Ambiguous | Recoverable | Modal with datasource options | Connection preserved | Select datasource |
| Permission denied | Permanent | "No access to this asset" | Connection preserved | Contact admin |

### Run
| Failure | Type | UI Response | State Preserved | Recovery |
|---------|------|-------------|-----------------|----------|
| SSE disconnect | Transient | "Reconnecting..." auto-retry | Run state preserved | Auto-reconnect with `last_seq` |
| Max retries exceeded | Transient | "Connection lost" + Manual Retry | Run state preserved | Click Retry |
| Run error (backend) | Permanent | Show error in timeline | Binding preserved | Start new run |
| 401 mid-stream | Permanent | "Session expired" + Re-auth | Binding preserved | Re-authenticate |
| Replay unavailable | Expected | Info banner + continue | Run state preserved | Automatic continue |

## Instrumentation Goals

Track these metrics to validate UX improvements:

### Core Funnel Metrics
| Metric | Definition | Target |
|--------|------------|--------|
| time_to_first_run | Notebook open → first timeline event | < 60s for new users |
| connect_success_rate | Successful connects / total attempts | > 95% |
| connect_test_failure_rate | Failed test connections / total tests | Track to debug wizard |
| attach_success_rate | Successful attaches / total attempts | > 90% |
| 409_frequency | 409s / total attach attempts | < 10% |
| 409_resolution_rate | 409s resolved via modal / total 409s | > 80% |
| gui_vs_magic_ratio | Sessions using GUI / sessions using magics | Trending toward GUI |
| reconnect_success_rate | Successful SSE reconnects / disconnects | > 90% |

### Confusion Metrics (Early Warning)
| Metric | Definition | Signal |
|--------|------------|--------|
| status_invocations_per_session | `%dataing status` calls per session | High → UX is unclear, user checking state repeatedly |
| clear_context_rate | `clear()` calls / total sessions | High → attach model is confusing |
| attach_switch_rate | Multiple `attach()` within 60s | High → typeahead results misleading or wrong asset selected |
| kernel_switch_confusion | State lookups for wrong kernel_id | High → sidebar not tracking active kernel properly |

Log these via standard telemetry adapter (existing pattern in `adapters/`).

## Risks

1. **React-in-Lumino complexity** - Embedding React requires careful lifecycle management
   - Mitigation: Use `ReactWidget.create()` pattern from JupyterLab examples; isolate React components

2. **Keyring cross-platform** - May not work in all Jupyter environments
   - Mitigation: 3-mode system with clear wizard detection + messaging

3. **Asset search performance** - Large catalogs (10k+ tables) may be slow
   - Mitigation: Server-side cursor pagination, debounced search, cache recent results

4. **Kernel-scoped state on kernel restart** - User loses context
   - Mitigation: Store `last_binding` per workspace_id in ISettingRegistry, offer "restore previous context" on kernel restart

5. **SSE resume with event expiry** - Long-running investigations may lose history
   - Mitigation: `replay_unavailable` event triggers info banner (not error) + continue from current + offer web UI link

6. **Workspace identity drift** - Different workspaces could get confused
   - Mitigation: workspace_id stored in ISettingRegistry per JupyterLab workspace; state keyed by both
