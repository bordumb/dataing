# fn-37.1 Implement get_relevant_code_changes function for asset lookup

## Description

Create a function that queries the `code_changes` table (from fn-36) to find recent commits affecting a given asset. This is the data layer that feeds code context into hypothesis generation. Changes are ranked by relevance: exact asset match > upstream dependency > file path match, and filtered by recency (configurable lookback, default 14 days, max 5 results).

### Implementation

1. Create a new module `python-packages/dataing/src/dataing/adapters/db/code_changes.py` with a `CodeChangesRepository` class:
   ```python
   class CodeChangesRepository:
       def __init__(self, db: AppDatabase) -> None: ...

       async def get_relevant_code_changes(
           self,
           tenant_id: str,
           asset_id: str,
           lookback_days: int = 14,
           max_results: int = 5,
       ) -> list[CodeChange]: ...
   ```

2. Define a `CodeChange` dataclass in `python-packages/dataing/src/dataing/core/domain_types.py`:
   ```python
   class CodeChange(BaseModel):
       commit_hash: str
       author_name: str | None
       message: str | None
       committed_at: datetime | None
       affected_assets: list[str]
       relevance_score: float  # 1.0=exact, 0.7=upstream, 0.4=path
   ```

3. The SQL query should:
   - JOIN `code_changes` with `git_repositories` on `repo_id` to scope by `tenant_id`
   - Filter `committed_at >= NOW() - interval '{lookback_days} days'`
   - Search `affected_assets` JSONB for the target `asset_id` (exact match gets score 1.0)
   - Also match partial path patterns from `dataset_repo_mappings` (score 0.4)
   - ORDER BY relevance_score DESC, committed_at DESC
   - LIMIT to `max_results`

4. Add unit tests in `python-packages/dataing/tests/unit/adapters/db/test_code_changes.py` that mock the database and verify ranking logic, lookback filtering, and max_results capping.
