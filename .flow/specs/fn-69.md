# Epic: Checks as Code

## Overview

Teams define data quality checks for each dataset once, in git: YAML files validated against the versioned `dataing/v1` spec. After that, checks re-run on demand or on a schedule, and changes are reviewed as pull requests. Failing checks open issues and trigger investigations, and investigations propose new checks.

This epic supersedes fn-47 (Scheduled Investigation Jobs) and fn-48 (Threshold-Based Auto-Investigation).

**The design is the source of truth:** `docs/plans/2026-09-26-checks-as-code-design.md`. Decisions D1–D11 and the §16 refinements are settled; tasks must not reopen them.

## Scope

**In scope:**
- The spec and loader, the SQL compiler, read-only validation and the condition evaluator.
- Two kinds of query identity in `QueryGateway`: the user, and an automation credential (D11).
- The runner on its own Temporal task queue (`checks`), with a per-datasource concurrency cap in Redis.
- The checks API and the CLI (`schema`, `validate`, `run`, `apply`).
- A Checks tab and a per-user credentials page.
- The failure loop: an intake service, incident handling and auto-investigation.
- Codify producing `CheckSpec`, and LLM-drafted starter suites.
- EE: schedules, a GitHub App for github.com and GHES, pull request previews, and pull requests opened by dataing.
- An edition switch for deployments, and a rescope of fn-13.

**Out of scope** (design §14):
- Editing checks inside dataing.
- Schema and contract checks.
- ML baselines.
- Warehouse cost caps.
- GitLab and Bitbucket.
- Commit sync on the webhook (fn-36 follow-up).
- Scorecards.
- Result retention.

- All 57 are folded into the task specs, and into design doc §17.
- Three tasks were added: fn-69.31 (credential isolation), fn-69.32 (non-blocking adapters with deadlines) and fn-69.33 (exports).
- Round 2 resolved 49 of the 57. Revision 2 fixes the rest, plus the new issues round 2 found. It adds fn-69.34 (tracked migration runner).
- Round 3 confirmed those fixes. Revision 3 closes the remaining gaps:
  - reserving warehouse capacity before a query is submitted;
  - a durable claim before a run starts;
  - skipped runs created and finalized atomically;
  - applying all of a run's incident effects in one transaction;
  - an execution receipt for investigations;
  - catch-up through the schedule's own trigger;
  - the migration runner moved up to gate M1, with demo seeds kept opt-in.
- Round 4: M4 passed (SHIP). Revision 4:
  - frees capacity only on positive evidence (BigQuery ID fencing, Postgres session checks, Snowflake/Trino history lookups, and an admin release for anything unresolved);
  - makes workflow admission a compare-and-swap that competes with abandonment;
  - replaces custom catch-up with Temporal's native catch-up, with the window sized to the cron's longest gap.

## Conventions (all tasks)

- **Ruff:** Google docstrings, including on `__init__`; lines of 100 characters or fewer; `X | Y` in isinstance; `raise … from e`.
- **Mypy:** strict for CE and EE. Logger calls take f-strings.
- **Editions:** CE never imports EE. EE extends CE through hooks (fn-69.21).
- **Migrations:**
  - Append-only, in `python-packages/dataing/migrations/`.
  - Idempotent, because `just demo-infra` re-runs every file.
  - Take the next free number when merging; 035 is already claimed on several branches.
- **Tests:**
  - pytest-asyncio in auto mode.
  - `@pytest.mark.integration` for tests that need Postgres or Redis. Integration Postgres runs in a throwaway container.
  - Use `uv run --frozen …`.
- **Commits:** `feat(fn-69): …` with a `Signed-off-by` trailer (CONTRIBUTING.md).

## Dependencies and risks

- **Fixes in flight, each in its own worktree:**
  - tenant ownership on investigations and the worker's datasource lookup;
  - query errors passed through as errors;
  - the ad-hoc SQL route and fail-open EE webhook verification, which changes `validate_query`;
  - the dataset Investigations tab query.

  fn-69.5, fn-69.6, fn-69.8 and fn-69.17 must rebase on these fixes.
- **CLI clash.** fn-55 plans a `dataing` console script in CE, which collides with the one in `dataing-cli`. fn-69.10 has to settle this (see open questions).
- **Epic IDs.** fn-55 and fn-56 are already used on other branches, so this epic is fn-69 on purpose.
- **sqlglot.** Its minor releases can break compatibility, so pin one minor version (fn-69.1).
- **GHES support.** GitHub supports roughly 3.19–3.22 today; M3 picks the minimum version.

## Open questions (defaults adopted; override in review)

1. **Where the CLI lives.** Default: the `dataing` package, alongside fn-55's console script. Alternative: `dataing-cli`, declaring `dataing` as a dependency.
2. **Flap cool-down.** Default: 24 hours.
3. **Notifications in v1.** Default: tenant-wide, naming the owner team.
4. **Minimum GHES version.** Decided in M3: the oldest release still supported when M3 ships.
