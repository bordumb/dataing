# Epic: Observability & SLOs with OpenTelemetry

## Summary

Add distributed tracing, metrics, and correlation IDs across API, queue, and worker using OpenTelemetry. Enable SLO monitoring for investigation latency and success rates.

## Problem

Currently:
- No distributed tracing across API → Queue → Worker
- No correlation IDs linking HTTP requests to background jobs
- No metrics for SLO monitoring (latency, error rates)
- OpenTelemetry dependencies exist but are unused
- Structlog is used but without trace context

## Goals

1. **Distributed Tracing**: Trace requests from API through queue to worker completion
2. **Correlation IDs**: Link all logs/spans for a single investigation
3. **Metrics**: Expose Prometheus metrics for SLOs
4. **Integration**: Bridge structlog with OpenTelemetry context

## Non-Goals

- Custom dashboards (use Grafana/Jaeger)
- Alerting rules (configure in external systems)
- Full APM (focus on investigation workflow tracing)

## Technical Design

### Architecture

```
┌─────────────────────────────────────────────────────────────────────┐
│                           OTEL Collector                            │
│                    (Jaeger / Prometheus / etc.)                     │
└─────────────────────────────────────────────────────────────────────┘
                    ▲                           ▲
                    │ traces                    │ metrics
┌───────────────────┴───────────────────────────┴─────────────────────┐
│                                                                      │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────────────┐   │
│  │   FastAPI    │───▶│    Redis     │───▶│       Worker         │   │
│  │  (OTEL Auto) │    │    Queue     │    │   (Arq + Maistro)    │   │
│  │              │    │              │    │                      │   │
│  │ traceparent ─┼────┼─ W3C ctx ────┼────┼─▶ extract ctx        │   │
│  │ + baggage    │    │ + enqueue_at │    │    linked spans      │   │
│  └──────────────┘    └──────────────┘    └──────────────────────┘   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### Key Design Decisions (Post-Review)

1. **Use FastAPIInstrumentor** instead of custom BaseHTTPMiddleware
   - More reliable, handles streaming/async correctly
   - Add thin middleware only for correlation ID

2. **Full W3C Context Propagation** through queue
   - Serialize `traceparent` + `tracestate` in job payload (not just trace_id)
   - Create producer span at enqueue, consumer span in worker
   - Use `propagate.inject()` / `propagate.extract()` for proper linking

3. **E2E SLO Timing**
   - Store `enqueued_at` timestamp in job payload
   - Calculate total latency = worker_complete - api_received
   - Queue wait time = worker_start - enqueued_at

4. **Low-Cardinality Metrics**
   - Remove `tenant_id` from metric labels (use span attributes instead)
   - Never log `step.input_data` in spans (PII risk)
   - Labels: `status`, `step_type` only

5. **Metrics Collection Strategy**
   - Use OTEL Collector sidecar for Prometheus scraping (no port conflicts)
   - Or: Single `/metrics` endpoint in API only, workers push to collector
   - Create instruments once at startup, not per-job

6. **Standard OTEL Env Vars**
   - Respect `OTEL_TRACES_SAMPLER`, `OTEL_RESOURCE_ATTRIBUTES`
   - Separate `OTEL_TRACES_ENABLED` and `OTEL_METRICS_ENABLED`
   - Idempotent initialization

### Components

1. **Telemetry Module** (`dataing/src/dataing/telemetry/`)
   - `config.py` - OTEL SDK initialization (idempotent, respects env vars)
   - `correlation.py` - Correlation ID middleware (thin, only sets header)
   - `context.py` - W3C context serialization for queue
   - `metrics.py` - Pre-registered metric instruments
   - `structlog_processor.py` - Inject trace context into structlog

2. **Database Schema**
   - Add `traceparent TEXT` column to `investigation_jobs` (not just trace_id)
   - Add `enqueued_at TIMESTAMPTZ` for SLO timing
   - Pre-launch: simple migration (no CONCURRENTLY needed)

3. **Integration Points**
   - API: `FastAPIInstrumentor.instrument_app()` + correlation middleware
   - Queue: Serialize W3C context + enqueued_at in payload
   - Worker: Extract context, create linked consumer span
   - Flow: Child spans for steps (no input data in attributes)

### Metrics (SLOs)

| Metric | Type | Labels | Purpose |
|--------|------|--------|---------|
| `investigation_e2e_duration_seconds` | Histogram | `status` | Total latency (API→complete) |
| `investigation_queue_wait_seconds` | Histogram | - | Queue wait time |
| `investigation_worker_duration_seconds` | Histogram | `status` | Worker processing time |
| `investigation_step_duration_seconds` | Histogram | `step` | Step-level latency |
| `investigation_total` | Counter | `status` | Success/failure rates |

Note: `tenant_id` moved to span attributes, not metric labels (cardinality).

### Configuration

Standard OTEL environment variables:
```bash
# Tracing
OTEL_TRACES_ENABLED=true
OTEL_SERVICE_NAME=dataing
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.1

# Metrics
OTEL_METRICS_ENABLED=true
OTEL_METRICS_EXPORTER=otlp  # Push to collector, not direct Prometheus

# Resource
OTEL_RESOURCE_ATTRIBUTES=service.version=1.0.0,deployment.environment=production
```

## Risks

1. **Performance**: OTEL overhead on hot paths
   - Mitigation: Sampling (10% default), async batch export

2. **Context Loss**: Async boundaries in Arq
   - Mitigation: Explicit W3C context serialization (not just trace_id)

3. **Cardinality**: Too many unique label combinations
   - Mitigation: No tenant_id in labels, no input_data in spans

## Pre-Launch Simplifications

Since we're pre-launch with no backwards compatibility requirements:
- Simple migrations (no CONCURRENTLY)
- No feature flags for gradual rollout
- Can break queue payload format directly
- No old/new code paths in worker

## Success Criteria

- [ ] Jaeger shows linked spans: API → Queue → Worker → Steps
- [ ] Correlation ID appears in all structlog entries for a request
- [ ] OTEL Collector receives traces and metrics
- [ ] E2E latency histogram includes queue wait time
- [ ] No metrics cardinality explosion after 1 week
