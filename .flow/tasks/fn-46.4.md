# fn-46.4 Add workspace_id to datasources, investigations, and core tables

## Description

Add a `workspace_id` foreign key column to all resource tables that need workspace scoping. This is
the highest-risk migration in the multi-workspace epic: it touches ~15 tables and every downstream
query must eventually filter by `workspace_id`. The column is nullable initially so existing data
continues to work -- fn-46.7 will backfill it with the Default workspace ID.

Depends on: fn-46.1 (workspaces table must exist).

### Implementation

2. Update SQLAlchemy models to include the new column. For each model, add:
   ```python
   workspace_id: Mapped[UUID | None] = mapped_column(
       ForeignKey("workspaces.id"), nullable=True
   )
   ```
   Models to update (in `python-packages/dataing/src/dataing/models/`):
   - `data_source.py` - `DataSource`
   - `investigation.py` - `Investigation`
   - `issue.py` - `Issue`
   - `notification.py` - `Notification`
   - `webhook.py` - `Webhook`
   - `api_key.py` - `ApiKey`

3. For models in EE that use raw SQL (not SQLAlchemy), note the column exists but do not change
   queries yet -- fn-46.5 handles filtering.

4. Key design decisions:
   - Column is NULLABLE now. fn-46.7 backfills + makes NOT NULL.
   - No CASCADE on workspace FK yet (workspace deletion requires moving resources first).
   - Index on `workspace_id` for every table that will be queried by workspace.
   - `permission_grants` gets `workspace_id` to enable workspace-scoped RBAC.
   - `api_keys` gets `workspace_id` so keys can be scoped to a workspace.

5. Verify which tables exist by checking the full migration set. Not all tables listed above may
   exist (some may have been dropped). Adjust the migration accordingly.

6. Add a test that verifies the migration applies cleanly and the columns exist:
