# fn-69.16 [M2] Check failure incidents, recovery and notifications

## Description
### Goal
Turn check results into issues **exactly once**, under concurrency, out-of-order completion, crashed runs, skipped runs and reducer crashes (design §7.1, §7.4, §7.5, §17).

### Implementation
- **Migration:**
  - `check_incident_state` with `(suite_id, check_key)` as its primary key, and these columns:
    - `open_issue_id`
    - `armed`
    - `human_closed_while_failing`
    - `recovered_at`
    - `last_outcome`
    - `error_streak`
    - `streak_notified`
  - `check_reducer_cursor`: per suite, `last_applied_seq`.
  - A partial unique index on `issues(tenant_id, source_fingerprint)` covering unfinished issues.
  - `notification_dedupe`.
- **The reducer:** one per suite (workflow `check-incidents-<suite_id>`, signal-with-start). It consumes `run_finalized` outbox rows (fn-69.8), strictly in `seq` order.
- **Each run is applied in one database transaction.** That transaction contains:
  - every check's incident-state change;
  - issue creation or updates **through intake inside that transaction** (fn-69.15);
  - notification dedupe rows;
  - the cursor advance.

  So a crash part-way through rolls back completely, and a retry re-applies from scratch. If the commit succeeded but its acknowledgement was lost, the retry sees the advanced cursor and does nothing. Investigation dispatch happens afterwards, through intents (fn-69.15).
- **Applying a run, per check in its pinned version:**
  - `skipped` markers change nothing, and checks missing from the version are ignored.
  - **Fail with no open issue:** intake, with fingerprint `<suite>:<key>` and external ID `<suite>:<key>:<first_failing_run>`.
  - **Fail with an open issue:** update the "still failing" event.
  - **Fail within 24h of auto-recovery:** reopen, with no new investigation.
  - **Closed by a person while still failing:** stay disarmed until a pass.
  - **Pass:** add "recovered", and use the conditional system resolve.
  - **Warn:** no issue.
- **Human transitions** (`routes/issues.py:550`) use conditional updates.
- **Notifications:** 3 automated-run errors in a row → one per streak; a dead automation credential → one per datasource. Both deduplicated, tenant-wide, naming the owner team.
- **Recovery:** a sweep re-signals any suite whose cursor lags behind a finalized run.
## Acceptance
- [ ] An interruption after the first of several checks has been applied → a retry gives **exact** streak counts and events, with no double increments. A lost acknowledgement after commit → no re-application.
- [ ] Reversed completion order gives the same outcome as applying in order; `fail → skipped → pass → fail` equals `fail → pass → fail`.
- [ ] Run A crashes or times out with partial results, then run B fails → B's incident is created. A lost reducer signal is recovered by the sweep.
- [ ] Two failing runs at the same moment → one issue. A human close racing a recovery loses neither. fail/pass/fail within 24h → one reopened issue and one investigation.
