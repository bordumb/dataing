# fn-69.2 [M1] One encryption helper that fails fast

## Description
### Goal
Replace the copied Fernet code with one helper, and refuse to start without a key (design §10.4). The credential schemas (fn-69.31), automation credentials (fn-69.14) and GitHub App keys (fn-69.23) depend on this.

### Context
- **Build on** `adapters/datasource/encryption.py:19-48`. Its `get_encryption_key()` already has `allow_generation`.
- **Copies to replace:**
  - `core/credentials.py:57,70`
  - `models/data_source.py:64-72`
  - `entrypoints/api/routes/datasets.py:30-46`
  - `entrypoints/api/deps.py:347-357`, with a random-key fallback at `:349`
  - `entrypoints/temporal_worker.py:124-157`
- **Key generation** stays only in explicit demo seeding (`demo/seed.py:59`).

### Implementation
- One module with `encrypt_bytes`/`decrypt_bytes`, `encrypt_json`/`decrypt_json` and `get_fernet()`. The key comes from `DATADR_ENCRYPTION_KEY`, then `ENCRYPTION_KEY`.
- The API and worker stop at startup with a clear message when no key is set, unless demo mode is explicitly on.
- Leave EE SSO's separate key alone (`dataing_ee/core/sso/encryption.py`).
## Acceptance
- [ ] `Fernet(` appears only in the helper; a test greps `python-packages/dataing/src`.
- [ ] Outside demo mode, the API and worker exit at startup when no key is set, and `just demo` still works.
- [ ] Existing encrypted datasource configs and user credentials decrypt unchanged.
- [ ] ruff and mypy are clean.
