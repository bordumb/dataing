# Git Integration for Pipeline Change Detection

**Plan ref:** Task 0.3.1
**Phase:** 0 (Foundation)
**Designation:** OSS (basic sync), Enterprise (scheduled/automatic sync)

## Overview

Create a git integration that tracks changes to pipeline code (dbt models, Airflow DAGs, Spark jobs). When investigating anomalies, the agent correlates timing with code deploys. This builds on the existing dataset-repo-mapping system (fn-32) by adding actual git repository connection, commit history sync, and code change parsing.

## Scope

- `git_repositories` table with OAuth credentials per provider
- `code_changes` table with commit parsing and affected asset detection
- GitHub/GitLab/Bitbucket OAuth provider implementations
- Periodic sync that pulls commit history (incremental)
- File changes parsed to extract table names and logic changes
- CLI commands: `dataing git connect`, `dataing git sync`, `dataing git list`
- API endpoints: CRUD for git repos, trigger sync, query changes

## Approach

1. Create DB migrations for `git_repositories` and `code_changes` tables
2. Build SQLAlchemy models and repository adapter in `adapters/db/`
3. Implement git commit parser (shell out to `git` for parsing commits, diffs)
4. Build asset matching: parse SQL/dbt refs from diffs to detect affected tables
5. Create API routes under `/api/v1/git/`
6. OAuth integration for GitHub initially (GitLab/Bitbucket follow)
7. Sync worker using existing background job infrastructure

## Data Model

```sql
CREATE TABLE git_repositories (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    name TEXT NOT NULL,
    url TEXT NOT NULL,
    provider TEXT NOT NULL,  -- github, gitlab, bitbucket
    access_token_encrypted TEXT,
    tracked_paths TEXT[],
    last_sync_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE code_changes (
    id UUID PRIMARY KEY,
    repo_id UUID REFERENCES git_repositories(id),
    commit_hash TEXT NOT NULL,
    author_name TEXT,
    author_email TEXT,
    message TEXT,
    committed_at TIMESTAMPTZ,
    affected_assets JSONB,
    raw_diff TEXT,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

## Risks

- Large repos slow to sync → Incremental sync, shallow clone
- OAuth token expiry → Refresh token handling, sync failure alerts
- Parsing SQL from arbitrary code → Start with dbt (structured), expand later

## Gap Analysis Risks

- **GitHub API rate limits**: PR metadata lookup during sync requires API calls. 5000 requests/hr limit for authenticated users. For a repo with 1000 commits in 14 days, that could be 1000 API calls just for PR metadata. Plan async enrichment with batching and rate limit handling.
- **Squash merges**: A squash merge creates a new commit that does not match the original PR commits. The PR lookup must map the merge commit back to the PR.
- **Force-pushed branches**: Commit hashes in `code_changes` may become dangling references after force-push.
- **Self-hosted git providers**: URL templates for `github.com` do not work for `github.acme.internal`. URL template must be configurable per repository.
- **Existing state**: Only ~15% built. The dataset-repo-mapping system (fn-32) exists but the full git sync infrastructure (git_repositories table, code_changes table, OAuth, commit parsing, sync worker) is entirely unbuilt.
