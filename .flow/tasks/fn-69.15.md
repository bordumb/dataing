# fn-69.15 [M2] Issue intake service shared by webhooks and checks

## Description
### Goal
One service handles dedupe → issue → policy → investigation. It survives retries and competing creators, and never runs an investigation twice, even after Temporal's retention period has passed (design §7.2, §16, §17).

### Context
- **Duplicated today:** CE `routes/integrations.py:290-341,401-625` and EE `routes/integrations.py:766`.
- **`investigations.status` is GENERATED** (`migrations/013_unified_investigation.sql:23`).
- **All creation paths count toward usage:** `adapters/entitlements/database.py:151` and `routes/investigations.py:412`.
- **Deployment to a populated database** requires the tracked migration runner (fn-69.34).

### Implementation
- **New code:** `services/issue_intake.py` and an `IssueRepository`.
  - Intake runs **inside a transaction the caller provides**, so the incident reducer (fn-69.16) can make the whole of a run's effects atomic.
  - It's callable from Temporal activities.
- **Migration:**
  - `investigation_intents`: investigation ID as primary key, `tenant_id`, `issue_id`, `dispatch_state`, `attempts`, `start_attempted_at`, `execution_receipt_at`, `workflow_run_id` and `created_at`.
  - `investigation_usage`: tenant plus month with a count, backfilled from the current month.
- **Authoritative usage:** every investigation creation path increments `investigation_usage` in its own transaction, with a conditional increment. At the limit, intake downgrades `auto` to `review`.
- **Intake transaction:**
  1. dedupe or create the issue;
  2. reserve usage;
  3. insert the `investigations` row and its `investigation_intents` row (`pending`).
- **Dispatch with an execution receipt:**
  1. Record `start_attempted_at`.
  2. Start the workflow with ID = investigation ID and `REJECT_DUPLICATE`.
  3. **The investigation workflow's first activity writes `execution_receipt_at`** (fn-69.17) **before any side effect**.
- **The dispatcher's rules for a pending intent:**
  - A receipt exists → mark it dispatched, and never start it again.
  - No receipt, and the workflow can be found with `describe` → mark it dispatched.
  - No receipt, and no workflow can be found → **safe to start again**. Without a receipt the workflow never got past its first step, so nothing happened. This holds even after the retention period.
- **System transition:** only OPEN or TRIAGED → RESOLVED, as a conditional update. Refactor both webhook routes to use the service.
## Acceptance
- [ ] Against the real migrated schema: an intent is written, and redispatch after a restart works.
- [ ] Completion, then the history expiring past retention, then a dispatcher restart → **no second execution** (the receipt exists). A crash before or after Temporal accepts the start → exactly one execution.
- [ ] Existing usage counts; concurrent manual creation and intake competing for the last slot → exactly one succeeds.
- [ ] Intake inside a caller's transaction rolls back cleanly. A system resolve works only from OPEN or TRIAGED.
