# fn-69.7 [M1] Per-datasource concurrency cap (Redis) and Redis client wiring

## Description
### Goal
Cap concurrent queries per **shared** datasource across all workers. A slot is freed **only on positive evidence** that its query has ended or was never submitted (design §5.3, §17).

### Scope
- Embedded engines (DuckDB, SQLite) run inside each worker's own process, so there's no shared warehouse capacity to protect. They use an in-process limiter per worker, and never touch the Redis registry.
- The global cap covers Postgres, Snowflake, BigQuery, Trino and other server engines.

### Implementation
- **New package** `dataing/adapters/concurrency/` with a `ConcurrencyLimiter` protocol.
  - `acquire()` returns a `Lease`: a unique token, an `asyncio.Event` called `lost`, and `release()`.
- **`RedisLeaseLimiter`:**
  - One ZSET of lease tokens per `{tenant}:{datasource}`, with expiry scores from Redis `TIME`.
  - **Acquire and Renew** are Lua scripts. Renew succeeds only while the token is held; otherwise it sets `lost`.
- **The execution registry, which doesn't expire:**
  1. **Before submission**, the runner writes a reservation keyed by a local **attempt token** (adapter, principal, `submit_by` deadline). The adapter refuses to submit after `submit_by`.
  2. After submission, the remote ID is attached.
  3. Acquire counts each attempt once.
  4. A registry entry is removed only when fn-69.32's `resolve_attempt` returns **`ended`** or **`never_submitted`**, both backed by positive evidence.
  5. **Elapsed time alone never frees a slot.**
- **Registry reconciler** (in the worker). It re-resolves entries whose lease has gone.
  - `running` or `unknown` keeps holding capacity. That fails closed.
  - After a horizon (default 2× the datasource's maximum statement timeout), an entry that's still `unknown` is **surfaced**: an admin notification, plus an entry in `GET /checks/capacity/{datasource}`.
  - An admin can **release it manually**, which is audited. Nothing is released automatically.
- **Failure handling:**
  - Bounded wait with jitter. `ConcurrencyBusyError` and `ConcurrencyUnavailableError` (Redis down) are both retryable, and when Redis is down no query runs.
  - `release()` only removes the lease.
- **Limit** from the adapter's `max_concurrent_queries`, with an env override. The Redis client is created in the worker.
## Acceptance
- [ ] With a limit of 2, five concurrent acquisitions never go above 2 (real Redis).
- [ ] A worker that dies after the warehouse accepted the query but before the ID was recorded, a lost submission response, and a cancel that was acknowledged while the job is still running: all keep the slot occupied until `resolve_attempt` returns positive evidence.
- [ ] **Delayed submission** (delivery beyond any margin, then worker death) keeps the slot occupied. There's no time-based release.
- [ ] An `unknown` entry past the horizon triggers one admin notification and appears in the capacity endpoint. A manual release is audited and frees the slot.
- [ ] DuckDB never uses the Redis registry.
