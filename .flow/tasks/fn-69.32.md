# fn-69.32 [M1] Non-blocking adapter execution with enforced query deadlines

## Description
### Goal
Adapter queries never block the event loop, deadlines and cancellation stop the query in the warehouse, and every attempt can be resolved from **positive evidence** after a crash (design §5.3, §17).

### Implementation
- **Blocking drivers** (DuckDB `sql/duckdb.py:230-243`, Trino `sql/trino.py:272`, Snowflake, BigQuery) run in a dedicated thread executor, where each connection is owned by one thread.
- **`execute_query(sql, *, attempt_token, submit_by, timeout_seconds)`:**
  - Refuses to send after `submit_by`.
  - Returns a handle with `remote_id`, `cancel()` and `confirm_terminated(timeout)`.
- **`resolve_attempt(attempt_token, principal)`** returns `ended`, `never_submitted`, `running` or `unknown`. It connects with the attempt's own principal, so the attempt is visible.

| Adapter | How the attempt is tagged | Positive evidence |
|---|---|---|
| **BigQuery** | job ID preassigned to the attempt token | `jobs.get` DONE → `ended`. On 404, **fence the ID** by inserting a trivial job with the same ID: success → the original can now never be created, but the slot is **held until the fencing job itself reaches DONE**, then `never_submitted`; 409 → poll the original |
| **Postgres** | `application_name = dataing:<attempt>`, set **and acknowledged** on the session before any check SQL; `submit_by` is checked again immediately before sending | No session with that name in `pg_stat_activity` **and** the client's `connect_timeout` has passed since `submit_by` → `ended` (a query needs its session, and no new session can be set up after the client's connect deadline) |
| **Snowflake** | `QUERY_TAG` = attempt token | `INFORMATION_SCHEMA.QUERY_HISTORY` by tag: a terminal status → `ended`; RUNNING or QUEUED → `running`; not found → `unknown` (hold) |
| **Trino** | attempt token in the query's **`source`** (client info), plus a leading SQL comment; `system.runtime.queries` exposes `source` and `query` but not client tags | Match on `source`: FINISHED or FAILED → `ended`; RUNNING or QUEUED → `running`; not found → `unknown` (hold) |
| **DuckDB, SQLite** | embedded | Not registered; see fn-69.7 |

- **Deadlines:**
  - DuckDB: `interrupt()`.
  - Trino: `query_max_run_time` plus a cancel request.
  - Snowflake: `STATEMENT_TIMEOUT_IN_SECONDS` plus an abort.
  - BigQuery: a job timeout plus `cancel_job`, then poll until DONE.
  - Postgres: `statement_timeout`.
- **On cancellation or a deadline:** `cancel()`, then `confirm_terminated`. If termination isn't confirmed, the attempt stays registered.
## Acceptance
- [ ] A long DuckDB query runs alongside a 1-second heartbeat without stalling it.
- [ ] Timeouts and cancellation stop the query in the warehouse on real DuckDB and Postgres.
- [ ] **Real Postgres:** a crash after acceptance → `running` while the session lives, then `ended`.
- [ ] **Real Trino** (container, `-m integration`): lose the submission acknowledgement, then `resolve_attempt` finds the query by `source` under the executing principal.
- [ ] **BigQuery** (mocked): the fencing insert on 404 → the slot is held until the fence job is DONE, then `never_submitted`; 409 → polls the original.
- [ ] **Postgres interleaving:** tagging is paused past `submit_by` → the check SQL is never sent.
- [ ] **Snowflake** (mocked): a missing history row → `unknown`.
- [ ] Existing adapter tests still pass.
