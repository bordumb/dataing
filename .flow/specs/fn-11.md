# System-Wide Serialization Strategy

## Overview

Refactor the codebase to eliminate fragile `json.dumps()` calls by implementing a centralized, robust serialization strategy leveraging Pydantic V2. This will resolve recurring runtime errors caused by non-serializable types (UUID, datetime, date) and ensure consistent JSON handling across API responses, database persistence, and message queue payloads.

## Scope

### In Scope
- Create a centralized serialization utility module (`dataing.core.serialization`)
- Refactor `AppDatabase` adapter to use robust serialization for JSONB columns
- Refactor API routes (`investigations.py`, `notifications.py`) to use Pydantic `model_dump_json()` or the new utility
- Refactor `worker.py` and other background tasks to use the new utility
- Refactor webhook payloads to ensure reliable delivery
- Add comprehensive unit tests for serialization of complex types

### Out of Scope
- Changing the underlying database JSONB column types
- Migrating existing data in the database (current data is assumed valid JSON)
- Performance optimization of serialization beyond what Pydantic V2 provides natively

### Phase 2: Database Layer Refactor

## Key Design Decisions

### Pydantic V2 as the Engine
We will leverage Pydantic V2's `pydantic_core` serialization, which is implemented in Rust and is significantly faster and more correct than Python's stdlib `json`.

### `to_json_string` Helper
Instead of sprinkling `TypeAdapter` instantiation everywhere, we will expose a simple functional interface:

```python
from pydantic import TypeAdapter
from typing import Any

_any_adapter = TypeAdapter(Any)

def to_json_string(obj: Any) -> str:
    """Robustly serialize any object to JSON string."""
    # model_dump_json handles datetime, uuid, etc. automatically
    return _any_adapter.dump_json(obj).decode("utf-8")
```

### Direct Model Usage
Where objects are already Pydantic models (e.g., `InvestigationContext`), we will prefer `obj.model_dump_json()` over the helper function to avoid unnecessary validation overhead, though the helper will support models too.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Performance regression | Pydantic V2 is generally faster than stdlib json; verify with benchmarks if concerned. |
| Double serialization | Careful audit of code paths to ensure we don't stringify an already-stringified JSON field. |
| Circular dependencies | Place the utility in `dataing.core` with zero internal dependencies. |

## Open Questions

1.  **Custom Encoders**: Do we have any weird custom types (e.g. from third-party libs) that Pydantic doesn't handle out of the box? *Assumption: No, mostly standard library types.*
2.  **ORJSON**: Should we use `orjson` directly for even more speed? *Decision: Stick to Pydantic for now for consistency and simplicity; upgrade to orjson only if profiling shows a bottleneck.*
