# fn-32 Dataset-to-Repository Mapping System

## Overview

Build a mapping layer that connects datasets to their source code repositories, enabling the investigation agent to correlate data anomalies with code changes. When an anomaly is detected (e.g., "nulls spiked at 2pm"), the system resolves which repo/file produces that dataset, and the agent uses **existing bond-agent tools** (`github_toolset`, `githunter_toolset`) to inspect recent commits, PRs, and blame information.

This is **not** a GitHub integration — bond-agent already provides `GitHubAdapter` (repo browsing, commits, PRs, code search) and `GitHunterAdapter` (blame, PR discussion, file experts). This system is purely the **mapping layer**: "dataset X is produced by repo Y, file Z."

## Why

Most data anomalies are caused by code changes. Without knowing which repo/file produces a dataset, the agent can't correlate anomalies with code changes. This is the foundation for CODE_CHANGE hypothesis generation.

## Approach

### Architecture: Three-Layer Resolution

1. **Explicit mappings** (priority=0, confidence=1.0) — User manually maps `analytics.orders` → `acme/etl-pipelines`, `dags/orders.py`
2. **Pattern rules** (priority=10, confidence=0.8) — User creates `analytics.*` → `acme/analytics-etl`, `models/{table}.sql`
3. **Auto-discovery** (priority=20, confidence=0.6-0.95) — OpenLineage `sourceCodeLocation` facet or dbt manifest import

Resolution: query all matching mappings for a dataset, sort by `(priority ASC, confidence DESC, created_at DESC)`, return best match. Cache results with TTL.

### Integration with Investigations

The mapping system is **read-only context** for the agent. During investigation:
1. Agent calls resolve endpoint with dataset_id
2. Gets back `repo_owner`, `repo_name`, `file_path`
3. Uses bond-agent's `github_get_commits` to find recent changes
4. Uses `githunter_toolset` for blame/PR analysis
5. Generates CODE_CHANGE hypothesis if relevant commits found

No new GitHub auth needed — bond-agent handles that via `GITHUB_TOKEN` env var and `BondToolDeps`.

### Data Model: `dataset_repo_mappings` (migration 030)

| Column | Type | Description |
|--------|------|-------------|
| id | UUID | PK, `gen_random_uuid()` |
| tenant_id | UUID | FK → tenants, ON DELETE CASCADE |
| dataset_pattern | TEXT | Exact name or glob pattern (normalized lowercase) |
| pattern_type | TEXT | 'exact', 'glob' |
| priority | INT | 0=explicit, 10=pattern, 20=discovered |
| repo_owner | TEXT | GitHub org or user |
| repo_name | TEXT | Repository name |
| file_path | TEXT | Path or pattern with `{table}`, `{schema}` tokens |
| branch | TEXT | Default branch to inspect (nullable) |
| job_name | TEXT | Optional: Airflow DAG, dbt model name |
| source | TEXT | 'manual', 'openlineage', 'dbt_manifest', 'bulk_import' |
| confidence | FLOAT | 0.0-1.0 |
| confirmed | BOOLEAN | false for suggestions, true for confirmed |
| metadata | JSONB | Source-specific data |
| last_verified_at | TIMESTAMPTZ | Last time confirmed by job run |
| created_at | TIMESTAMPTZ | DEFAULT NOW() |
| updated_at | TIMESTAMPTZ | DEFAULT NOW() |

### API Endpoints

All under `/api/v1/dataset-repo-mappings`, tenant-scoped via `AuthDep`.

| Method | Path | Purpose |
|--------|------|---------|
| POST | `/dataset-repo-mappings` | Create mapping |
| GET | `/dataset-repo-mappings` | List with filters |
| PUT | `/dataset-repo-mappings/{id}` | Update mapping |
| DELETE | `/dataset-repo-mappings/{id}` | Delete mapping |
| POST | `/dataset-repo-mappings/bulk` | Bulk import (JSON array) |
| POST | `/dataset-repo-mappings/import-dbt-manifest` | Import from manifest.json |
| GET | `/dataset-repo-mappings/suggestions` | List unconfirmed discoveries |
| POST | `/dataset-repo-mappings/{id}/confirm` | Promote to confirmed |
| POST | `/dataset-repo-mappings/{id}/dismiss` | Delete suggestion |
| GET | `/datasets/{dataset_id}/repo` | Resolve best repo match |

### Pattern Matching

- Patterns normalized: lowercase, `schema.table` format
- Glob uses `fnmatch` in Python after loading candidate patterns from DB
- Match against both `schema.table` and `database.schema.table` forms
- Resolution: exact matches first → glob evaluation → sort by `(priority, -confidence, -created_at)` → return first

### Discovery Sources

**dbt Manifest Import**: Parse `manifest.json`, extract `original_file_path` per model. User provides repo info at import time. `source='dbt_manifest'`, `confirmed=false`, `confidence=0.85`.

**Bulk Import**: JSON array with `dataset_pattern`, `repo_owner`, `repo_name`, `file_path`. Created as `source='bulk_import'`, `confirmed=true`, `priority=0`.

**OpenLineage** (EE/Future): Hook into lineage adapter, upsert from `sourceCodeLocation` facet.

### CLI Commands (Typer, in `dataing-cli/`)

- `dataing show-repo <dataset>`
- `dataing map-repo --list`
- `dataing map-repo --suggestions`
- `dataing map-repo --confirm <id>`
- `dataing map-repo --import-dbt <manifest.json> --repo <owner/repo>`

### Graceful Degradation

Missing mapping → investigation continues without code context. No error, skip CODE_CHANGE hypothesis. Log at DEBUG.
