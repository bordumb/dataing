# Docker Compose Self-Host Bundle

**Plan ref:** Task 1.1.2
**Phase:** 1 (Distribution)
**Designation:** OSS

## Overview

Create a production Docker Compose configuration that spins up the complete Dataing stack for self-hosted deployment. Includes API server, Temporal server, workers, PostgreSQL, and Redis.

## Scope

- Production Dockerfiles (backend, frontend) with multi-stage builds
- Production docker-compose.yml with all services
- Health checks on all services
- Persistent volumes for data
- Environment variable documentation
- Development mode vs production mode configs

## Existing State

- `demo/docker-compose.demo.yml` exists (7 services, demo-specific)
- Release workflow references `infra/Dockerfile.backend` and `infra/Dockerfile.frontend` but files don't exist
- No Temporal server in existing compose

## Key Files

- `docker-compose.yml` (new, production)
- `infra/Dockerfile.backend` (new)
- `infra/Dockerfile.frontend` (new)
- `demo/docker-compose.demo.yml` (reference)

## Quick Commands

```bash
docker compose up -d
docker compose ps
docker compose down -v
```

## Acceptance

- `docker compose up` starts full stack (API, Temporal, workers, PostgreSQL, Redis)
- Default configuration works out of box
- Health checks on all services
- Persistent volumes for PostgreSQL and Redis
- `docker compose down -v` cleanly removes everything
- Works on Linux, macOS (Intel + Apple Silicon)
- Startup < 60 seconds on warm cache

## Dependencies

- fn-40 (PyPI packages) for worker dependencies
- fn-13 (Helm Charts) is 0/6 done. Docker images should be designed to work for both Compose and Helm. Coordinate image tagging, registry strategy, and multi-arch builds.

## Gap Analysis Risks

- **Stale demo compose**: `demo/docker-compose.demo.yml` uses Arq/Redis worker (`python -m dataing.entrypoints.worker`), not Temporal. Since fn-16 (Temporal Migration) is complete, the demo compose is now stale and cannot be used as-is.
- **Missing Dockerfiles**: Release workflow references `infra/Dockerfile.backend` and `infra/Dockerfile.frontend` but neither file exists. These must be created from scratch.
- **Temporal resource requirements**: Temporal server itself requires 2-4GB RAM. Combined with PostgreSQL, Redis, API, and workers, total could exceed 8GB. The "4GB RAM, 2 CPU" minimum from plan.md may be unrealistic.
- **Temporal persistence**: Temporal needs its own database (supports PostgreSQL but requires its own schema). Must decide whether to share the PostgreSQL instance or require a separate one.
- **LLM API key requirement**: The investigation engine needs `ANTHROPIC_API_KEY`. Without it, no investigations can run. The compose must clearly communicate this dependency with documentation and startup checks.
- **No Dockerfile for backend**: The existing demo compose references `./backend/Dockerfile` but no Dockerfile exists at the project root or backend path.
- **First-run initialization**: Demo compose uses hardcoded demo key `dd_demo_12345`. Production compose needs a way to generate initial API keys/admin accounts.
