# fn-69.22 [M3] Schedules: one Temporal Schedule per suite

## Description
### Goal
Automated runs whose state always matches one rule, dispatched per occurrence, with **native** catch-up and no custom recovery bookkeeping (design §5.5, §17).

### Implementation
- **One desired-state rule:** a suite should be scheduled when it's active, has a `schedule`, the tenant is entitled, and its datasource has an automation credential. It's recomputed by every hook and every reconciliation pass.
  - The rule holds → active.
  - Not entitled, or no credential → paused, with the reason stored.
  - `schedule:` removed, or the suite inactive → deleted.
- **The Schedule's action is a dispatcher.** Schedule `check-suite-<id>`, with overlap SKIP, jitter and the suite's time zone, starts `ScheduledCheckDispatchWorkflow(suite_id)`. The dispatcher:
  1. admits its occurrence (`TemporalScheduledStartTime`) through `check_schedule_admissions`, which is UNIQUE on `(suite_id, scheduled_time)`;
  2. re-evaluates the rule. If the suite is ineligible, it calls `create_skipped_run`, which inserts and finalizes the run atomically;
  3. otherwise it creates the pinned run and starts the child through fn-69.8's start protocol;
  4. **waits for the child to finish**, so SKIP covers the warehouse work.
- **Catch-up after downtime is Temporal's native behavior, sized so it's always correct.**
  - `catchup_window` = the **longest gap between consecutive occurrences** of the suite's cron in its time zone, computed over the next 366 days so DST is included, then capped at 7 days. A sparse cron with fewer than 2 occurrences in that horizon (annual, leap-day) uses the 7-day cap.
    - hourly → 1h
    - weekdays at 09:00 → 72h
  - Temporal filters missed occurrences by **each occurrence's age**, not by how long the outage lasted. Occurrences older than `catchup_window` are discarded; recent ones stay eligible under SKIP.
  - So after any outage, the latest missed occurrence is caught up whenever it's within the window. That's always true for crons whose gap is within the cap.
  - With overlap SKIP, a backlog turns into a run that's in flight while the others are skipped, never a sequential replay.
  - There are no custom recovery batches or counters, so deleting or recreating a Schedule has no state to reset.
  - The computed window is part of the desired configuration that the reconciler compares.
- **Upsert:** call `create_schedule`; if it raises `ScheduleAlreadyRunningError`, call `handle.update()` with an updater that has no side effects.
- **Reconciler:** compares the normalized observed Temporal configuration (calendars, action, policies including `catchup_window`, and paused state) with the desired configuration, reapplies on drift, and persists the applied marker afterwards.
- **CE:** a `schedule:` in a suite shows a notice.
## Acceptance
- [ ] `start_local()` tests:
  - overlap is skipped while a child is still running;
  - consecutive firings across a suite revision pin the right versions;
  - a lost start acknowledgement admits the occurrence once;
  - an ineligible suite gives an atomic skipped run, and a later failing run still creates its incident.
- [ ] Catch-up on a real server:
  - a 3-hour outage on an hourly schedule → one prompt run after recovery, not three;
  - a weekend outage on a weekday cron → one run;
  - an **eight-day outage on an hourly schedule** → occurrences older than the window are discarded, the most recent one runs promptly under SKIP, and there's no replay;
  - delete/recreate the Schedule, then another outage → the same behavior (no stale state).
- [ ] `catchup_window` computation is unit-tested for hourly, daily, weekday-only, DST-crossing, **annual and leap-day** crons (sparse → the 7-day cap).
- [ ] Downgrade then credential rotation → stays paused; removing `schedule:` deletes the Schedule; external changes are repaired.
