# fn-69.30 [M4] Rescope the Helm epic (fn-13) for GHES self-hosting

## Description
### Goal
Make fn-13 cover what GHES customers need, and gate M4 on a real install (design §10.2, §17).

### Implementation
Update `.flow/epics/fn-13.md` and its tasks in `.flow/tasks/fn-13.*`:
- **Temporal:** through the official chart (server only; you bring Postgres) or an external endpoint, using fn-69.29's startup order, including namespace registration.
- **Migrations:**
  - Replace the **pre-install migration hook** (`fn-13.3.md:25-27`). It deadlocks on the bundled Postgres, because Helm runs hooks before it creates the release's resources.
  - Use an ordinary Job, and gate the app on it.
- **Strict migrations:**
  - They must fail loudly and verify the schema; `infra/init-app-db.sh:27` suppresses errors today.
  - Prerequisite: fix migration 008's `teams` re-creation, so `ON_ERROR_STOP` works.
- **pgvector:** required for the bundled database and for external ones (`migrations/012_agent_memories.sql:6`), including the privilege to create extensions. An unsupported database fails clearly.
- **Frontend:**
  - `infra/nginx.conf:22` hardcodes Docker's resolver, `127.0.0.11`.
  - Use Kubernetes-compatible upstream resolution, or route `/api/` straight to the backend through the ingress.
  - Either way, preserve `/api/v1/github/webhooks/{app_id}`.
- **EE values and secrets:** the encryption key and `DATAING_PUBLIC_URL`; SaaS-only app variables are optional (fn-69.23 / fn-69.29).
- **M4 gate:** name one concrete fn-13 integration task as the gate. Its evidence is `helm install --wait` on kind showing:
  - an EE workflow completing;
  - frontend → API;
  - a signed webhook arriving through the ingress;
  - pinned versions.
## Acceptance
- [ ] The fn-13 spec and tasks are updated, and `flowctl validate --epic fn-13` passes.
- [ ] fn-13 has a named integration task that gates M4, with the evidence listed above.
