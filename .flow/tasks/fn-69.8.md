# fn-69.8 [M1] Check runner, Temporal workflow and the checks worker

## Description
### Goal
Run one suite end to end, correctly under retries, crashes, timeouts, skips and **every** dispatcher/reconciler interleaving (design §5.1, §5.4, §17).

### Execution boundary
- `CheckSuiteRunWorkflow` runs one `run_suite` activity, which owns the gateway session (fn-69.6).
- Checks run with bounded parallelism (4). Each result is persisted as it completes, keyed on `(run_id, check_key)`, and the completed keys are heartbeated.
- Retries skip checks that are already committed. Non-retryable or exhausted failures are persisted as `error`.

### Start protocol: one row, one winner
- **`check_runs` start columns:** `start_state` (`pending_start`, `starting`, `started` or `abandoned`), `start_workflow_id`, `start_deadline`.
- **Dispatcher** (the API or fn-69.22):
  1. CAS `pending_start` → `starting`.
  2. Start `check-run-<run_id>` with `REJECT_DUPLICATE`.
  3. Its later "record started" is an **idempotent no-op** when the state is already `started`, and **never** revives `abandoned`.
- **Workflow admission is itself a CAS.** The first activity runs:
  ```sql
  UPDATE check_runs
  SET start_state = 'started', start_workflow_id = :wid
  WHERE id = :id
    AND start_state IN ('pending_start', 'starting')
    AND finalized_at IS NULL
  ```
  If the state is already `started` with the same `:wid`, admission is idempotent (an activity retry).
  - 0 rows updated, and the state isn't `started` by this workflow → the workflow **exits without touching the warehouse**.
- **Reconciler abandonment is a CAS on the same predicate:** `start_state IN ('pending_start', 'starting') AND start_deadline < now() AND finalized_at IS NULL` → `abandoned`, then `finalize_run`.
  - Admission and abandonment race on the same row, and exactly one wins.
  - The reconciler's earlier `describe` is only a hint.

### Finalization (shared, idempotent, complete)
`finalize_run(run_id, terminal_status)`, in one transaction:
1. keeps committed results;
2. writes a result or marker for every check in the pinned version (`error`, or `skipped`);
3. sets `finalized_at`, after which late writes are rejected;
4. inserts one `run_finalized` outbox row.

`create_skipped_run` inserts and finalizes a skipped run in one transaction.

### Run reconciler
Every 5 minutes, it recovers every row with `finalized_at IS NULL`: it abandons through the CAS, finalizes dead workflows, and finalizes terminal rows that are missing their finalization.

### Runner core, principal and lease
- **Ports:** `dataing/checks/runner.py` works over the ports (server, local fn-69.10 and preview fn-69.27), with a `ResolvedSuite` as input.
- **Principal:** manual runs use `UserPrincipal`, everything else `AutomationPrincipal`, with the actor set per execute call.
- **Before each query**, reserve an attempt (fn-69.7). A lost lease cancels the query (fn-69.32).

### Worker
A second `Worker` on task queue `checks`, with explicit `max_concurrent_activities`.
## Acceptance
- [ ] Deterministic interleaving tests where exactly one transition wins:
  - pause the reconciler **after its `describe` found nothing**, admit the workflow, then resume the abandonment CAS → admission wins, and the run completes normally;
  - pause **after the abandonment CAS**, then let the workflow try admission → the workflow exits with no warehouse calls;
  - a dispatcher pausing between the start and "record started" never revives an abandoned run.
- [ ] A worker dying mid-suite leads to a retry that runs only the missing checks; a lost acknowledgement doesn't re-execute a check.
- [ ] Run A times out with partial results, then run B fails → A is finalized with markers, and B's incident is created (fn-69.16).
- [ ] A late result write after finalization is rejected; a lost completion notification gives exactly one outbox row.
