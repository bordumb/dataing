# Issues and Investigations System

## Overview

Add Issues as a first-class object for intake, triage, collaboration, and workflow management. Issues spawn Investigations (0..N) via human action or automation rules, maintaining clear separation between collaboration/workflow (Issues) and execution/analysis (Investigations).

## Scope

### In Scope (CE - Community Edition)
- Core Issue model with lifecycle states (OPEN → TRIAGED → IN_PROGRESS → BLOCKED → RESOLVED → CLOSED)
- Issue CRUD APIs with comments, labels, relationships, watchers
- Issue → Investigation linking (spawn from Issue)
- Frontend: /issues list, /issues/new, /issues/:id workspace
- SSE streaming for real-time issue updates
- Basic SLA tracking: derived timers (not constantly written), background job for breach detection, `sla_policy_id` nullable with default policy per tenant
- Issue events/activity timeline
- Permissions enforcement: dataset-aware visibility + investigation spawn permission
- Generic webhook ingest: POST /api/integrations/webhook-generic (signed shared secret) for creating issues without provider adapters

### In Scope (EE - Enterprise Edition)
- External integration webhooks (Jira, Monte Carlo, Great Expectations, Slack)
- Automation rules engine for auto-triggering investigations
- Advanced notification subscriptions
- Issue deduplication/correlation algorithms
- Runbook/knowledge base generation from resolved issues

### Out of Scope (Future)
- Custom fields per tenant
- Issue subtasks/checklists
- Time tracking
- Comment reactions

## Approach

### Phase 1: Data Model (CE)
- Add migration with core tables: `issues`, `issue_labels`, `issue_comments`, `issue_events`, `issue_relationships`, `issue_watchers`, `issue_investigation_runs`
- Follow existing patterns: BaseModel, tenant_id FK, UUID primary keys, `number` sequence per tenant
- Add Postgres GIN index for full-text search: `to_tsvector('english', title || ' ' || description)`
- `issue_investigation_runs` includes: `focus_prompt`, `execution_profile`, `trigger_type`, `trigger_ref` (JSONB), optional `approval_status` (queued/approved/rejected)

### Phase 2: Backend APIs (CE)
- Issues CRUD: GET/POST/PATCH /api/issues
- Comments: GET/POST /api/issues/:id/comments
- Relationships: POST /api/issues/:id/relationships
- Investigation spawn: POST /api/issues/:id/investigation-runs
- Events/timeline: GET /api/issues/:id/events
- SSE stream: GET /api/issues/:id/stream

### Phase 3: Frontend Foundation (CE)
- IssueList page with filtering, sorting, pagination
- IssueCreate page with templates
- IssueWorkspace with sidebar, timeline, comments
- Real-time updates via SSE

### Phase 4: Integration Webhooks (EE)
- Webhook endpoint per provider with signature verification
- Idempotency via `integration_events` table
- Adapter pattern for payload mapping to Issue fields

### Phase 5: Automation Rules (EE)
- Rules engine with conditions (JSON DSL) and actions
- Rate limiting per rule/tenant
- Dry-run support for testing

### Phase 6: Notifications & SLA
- **CE**: Core issue watchers, basic notification delivery, SLA breach detection background job
- **EE**: Advanced subscriptions/routing, escalation chains, multi-channel delivery
- Notification outbox pattern for reliable delivery
- SLA timers as derived fields; breach detection writes `issue_events` + enqueues notifications

### Phase 7: Knowledge Base (EE)
- Runbook model and APIs
- Generation from resolved issues + investigation synthesis
- Similarity-based suggestions

- [ ] SSE streaming delivers real-time updates
- [ ] Webhook integrations (EE) create Issues from external alerts
- [ ] Automation rules (EE) can auto-trigger investigations
- [ ] SLA tracking and breach notifications work
- [ ] Runbook generation (EE) captures resolution patterns
- [ ] All pre-commit checks pass (ruff, mypy)
- [ ] Test coverage maintained (unit + integration)
- [ ] **Dataset permissions enforced**: users without dataset permission cannot see issue contents (redacted stubs shown instead)
- [ ] **Investigation spawn permission**: only users with dataset permission can spawn investigations
- [ ] **Watchers respect access**: notifications do not leak dataset-restricted content via Slack/email
- [ ] **Webhook idempotency**: generic ingest cannot create duplicate issues for same provider event
- [ ] **Investigation runs store metadata**: trigger_type, trigger_ref, focus_prompt visible on Issue workspace

## Key Decisions

1. **State Transitions**: Relaxed assignee constraint to support triage queues and on-call rotations
   - OPEN → TRIAGED (any user)
   - TRIAGED → IN_PROGRESS/BLOCKED (requires assignee OR `acknowledged_by` field)
   - IN_PROGRESS ↔ BLOCKED (any assigned/acknowledged user)
   - IN_PROGRESS → RESOLVED (requires resolution note OR linked investigation synthesis OR runbook)
   - RESOLVED → CLOSED (any user)
   - CLOSED → OPEN (reopening, any user)

2. **CE/EE Split**: Core CRUD, Investigation linking, generic webhook ingest in CE; Provider adapters, Rules, Runbooks in EE

3. **Issue ID Format**: UUID internally, display as `#<number>` (bigint sequence per tenant)

4. **Deduplication**: Two-tier fingerprint strategy
   - **Primary**: `(tenant, source_provider, source_external_id)` when external ID present
   - **Secondary**: `(dataset_id, source_provider, dimension, monitor_id/check_id, optional time_bucket)`

5. **Investigation Completion**: Auto-post synthesis summary as comment AND attach structured fields to run record (`confidence`, `root_cause_tag`); do NOT auto-resolve (human decision)

6. **Permissions**: Issue visibility and notifications must not leak dataset-restricted content; investigation spawning requires dataset permission

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Webhook replay attacks | Timestamp validation + idempotency table with TTL |
| Rule infinite loops | Max rule depth + circuit breaker per issue |
| Large payload DoS | Size limits on webhook payloads (1MB) |
| SSE connection leaks | Heartbeat timeout + client disconnect detection |
