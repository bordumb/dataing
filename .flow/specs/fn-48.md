# Threshold-Based Auto-Investigation

**Plan ref:** Task 2.3.2
**Phase:** 2 (Enterprise)
**Designation:** Enterprise

## Overview

Define thresholds on data quality metrics (null rate, row count, freshness) that automatically trigger investigations when breached. Bridge between monitoring and investigation.

## Scope

- `thresholds` table with metric conditions
- Threshold CRUD API routes
- Evaluation engine (scheduled, not real-time)
- Auto-trigger investigation on breach with cooldown
- Threshold state machine: normal -> breached -> recovering
- CLI commands: `dataing threshold create`, `dataing threshold list`
- Integration with alert webhook for deduplication

## Data Model

```sql
CREATE TABLE thresholds (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    asset_id UUID NOT NULL,
    metric_name TEXT NOT NULL,
    operator TEXT NOT NULL,  -- gt, lt, eq, gte, lte
    value NUMERIC NOT NULL,
    severity TEXT DEFAULT 'warning',
    cooldown_hours INT DEFAULT 24,
    is_active BOOLEAN DEFAULT TRUE,
    last_evaluated_at TIMESTAMPTZ,
    state TEXT DEFAULT 'normal',
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

## Acceptance

- Define threshold: asset, metric, condition, value
- Threshold evaluation on configurable frequency
- Auto-trigger investigation on breach
- Cooldown prevents re-triggering within window
- Severity levels: info, warning, critical
- Hysteresis: require sustained breach before trigger
- CLI management commands

## Gap Analysis Risks

- **Metric collection source**: Spec does not specify where metrics come from. Does Dataing query the datasource directly to compute null_rate/row_count? Or consume metrics from external systems? This is a fundamental design decision.
- **Metric computation cost**: If Dataing queries the warehouse to compute null_rate for 100 columns across 50 tables every hour, that is 5000 queries/hour. Customer warehouse compute costs could be surprising.
- **Hysteresis details**: "Require sustained breach before trigger" needs specifics: how many consecutive breaches? Over what time window? Is this configurable per threshold?
- **State machine transitions**: What triggers `breached` -> `recovering`? What triggers `recovering` -> `normal`? Is `recovering` even necessary as a distinct state?
- **Dedup with alert webhooks**: If a Monte Carlo alert and a threshold breach both fire for the same issue, dedup must work across different codepaths with different dedup keys.
- **Custom metric thresholds**: Can a threshold be set on a custom SQL query result (e.g., "ratio of orders to customers should be between 5 and 20")? Or only predefined metric types? This determines usefulness.
