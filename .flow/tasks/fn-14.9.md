# fn-14.9 Jira and external provider webhook adapters (EE)

## Description

Create webhook adapters for Jira, Monte Carlo, Great Expectations, and Slack (EE).

### Adapter Pattern
Each adapter implements:
- `verify_signature(request)` - Provider-specific verification
- `parse_payload(body)` - Extract issue fields from provider payload
- `get_fingerprint(payload)` - Generate dedup key

### Providers
- Jira: X-Atlassian-Webhook-Id header, changelog parsing
- Monte Carlo: Custom HMAC, incident/alert payloads
- Great Expectations: Checkpoint result parsing
- Slack: X-Slack-Signature header, event subscription

### Implementation
- Create adapter base class in `dataing-ee/src/dataing_ee/adapters/integrations/`
- One adapter file per provider
- Registry for adapter lookup by provider name

## Done summary
Base adapter infrastructure:
- IntegrationAdapter base class with signature verification, payload parsing, fingerprinting
- AdapterRegistry for provider lookup by name
- Helper methods for HMAC-SHA256, nested value extraction, field mappings

Jira adapter:
- X-Hub-Signature verification (sha256=...)
- Parses issue.fields.summary, description, priority, labels
- Fingerprints via X-Atlassian-Webhook-Id or issue.id+event
- Filters to issue_created/updated events

Monte Carlo adapter:
- X-MC-Signature verification (raw HMAC)
- Handles incident and alert payloads
- Extracts severity, tables, impact
- Skips resolved/closed events

Great Expectations adapter:
- X-GE-Signature verification (sha256=...)
- Parses checkpoint validation results
- Determines severity from success_percent
- Only processes failed validations

Slack adapter:
- X-Slack-Signature verification (v0:{timestamp}:{body})
- Timestamp replay protection (5 min window)
- Handles event_callback, shortcut, interactive payloads
- Trigger reactions: bug, warning, fire, alert, etc.
- Skips bot messages and url_verification challenges

EE model updates:
- Added monte_carlo, great_expectations, slack to IntegrationProvider

- Updated routes VALID_PROVIDERS pattern

Tests:

- Fingerprinting tests

Why:
- Provides clean adapter pattern for integrating external systems
- Each adapter encapsulates provider-specific logic

- Field mappings allow customization per integration
