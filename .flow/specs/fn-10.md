# Durable Execution Engine

## Overview

Replace the current `asyncio.create_task()` pattern for investigation execution with a durable, distributed job queue using Redis + Arq. Investigations will survive worker crashes, API restarts, and horizontal scaling through checkpoint-based recovery.

## Scope

### In Scope
- Redis + Arq queue for job processing
- Postgres `investigation_jobs` table for checkpoint state
- Worker entrypoint with graceful shutdown (SIGTERM handling)
- Orchestrator modifications for checkpoint callbacks
- API integration (enqueue instead of `asyncio.create_task`)
- Docker Compose additions (Redis service)
- Kubernetes manifests (worker Deployment, KEDA ScaledObject)
- Unit and integration tests

### Out of Scope
- Prometheus metrics/observability (follow-up epic)
- Admin tooling for job inspection/cancellation (follow-up epic)
- Multi-priority queues per tenant tier (follow-up epic)
- Dead letter queue handling UI (follow-up epic)

## Key Design Decisions

### Checkpoint Storage
Use dedicated `investigation_jobs` table with JSONB `checkpoint` column. This separates job execution state (retries, lock, worker) from investigation domain state (snapshots, branches). The `InvestigationContext` Pydantic model serializes cleanly to JSONB.

### Lock Strategy
Keep existing `execution_locks` for branch-level locking. Use `investigation_jobs.worker_id` for job-level ownership. The two serve different purposes:
- `execution_locks`: Prevent concurrent writes to same branch
- `investigation_jobs.worker_id`: Track which worker owns the job

### Adapter Reconstruction
Workers must reconstruct tenant datasource adapters without API request context. Strategy:
- Job payload includes `tenant_id` and `datasource_id`
- Worker queries `datasources` table for encrypted connection config
- Worker decrypts using `ENCRYPTION_KEY` from environment
- Creates fresh adapter instance per job

### Branch Parallel Execution
When maistro emits BRANCH signal:
1. Parent job creates child jobs (one per branch spec)
2. Parent job sets status to `awaiting_merge`
3. Child jobs execute independently
4. Last child to complete triggers MERGE
5. Parent job resumes

### Idempotency
Steps must be idempotent for at-least-once delivery:
- `ExecuteQueryStep`: Use query hash as idempotency key, skip if result exists
- `GenerateQueryStep`: Cache LLM responses by prompt hash
- `SynthesizeStep`: Idempotent (overwrites synthesis field)

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Redis unavailable | API returns 503, frontend shows "Service temporarily unavailable" |
| Worker crashes mid-step | Checkpoint ensures resume from last completed step |
| Large context exceeds JSONB limits | Add size check, truncate query results if needed |
| Lock TTL expires during long step | Refresh lock periodically during step execution |
| Thundering herd on Redis reconnect | Exponential backoff with jitter in connection retry |
