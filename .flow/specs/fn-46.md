# Multi-Workspace Support

**Plan ref:** Task 2.2.1
**Phase:** 2 (Enterprise)
**Designation:** Enterprise

## Overview

Allow organizations to create multiple workspaces (sub-tenants) for team isolation. Each workspace has its own datasources, investigations, and users with separate role assignments.

## Scope

- `workspaces` and `workspace_members` tables
- Workspace CRUD API routes
- Add `workspace_id` to datasources, investigations, and other core tables
- Workspace-scoped query filtering throughout the system
- CLI commands: `dataing workspace list`, `dataing workspace switch`
- Migration path: existing data goes to "Default" workspace

## Data Model

```sql
CREATE TABLE workspaces (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    name TEXT NOT NULL,
    slug TEXT NOT NULL,
    settings JSONB,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (tenant_id, slug)
);

CREATE TABLE workspace_members (
    workspace_id UUID REFERENCES workspaces(id),
    user_id UUID REFERENCES users(id),
    role_id UUID REFERENCES roles(id),
    PRIMARY KEY (workspace_id, user_id)
);
```

## Acceptance

- Organization can have multiple workspaces
- Datasources and investigations scoped to workspace
- Users can belong to multiple workspaces with per-workspace roles
- API keys scoped to workspace
- CLI workspace management commands
- Existing data migrated to "Default" workspace

## Dependencies

- fn-7 (RBAC Enforcement, 0/7 done) for role assignment per workspace. Multi-workspace requires RBAC to be workspace-scoped.

## Gap Analysis Risks (HIGH RISK)

This is the highest-risk database change on the roadmap.

- **Migration scope**: No `workspace_id` exists on ANY table currently. Adding it to ~15+ tables (investigations, data_sources, alerts, audit_logs, issues, team_policies, sdk_bundles, dataset_repo_mappings) is a massive schema migration.
- **Every query must filter by workspace_id**: Missing this on ANY query is a cross-workspace data leak. Requires exhaustive audit of every repository method.
- **RBAC permission_grants**: Migration `008_rbac_tables.sql` does not have a `workspace_id` column. Permissions need to be workspace-scoped.
- **API key scoping**: Current auth uses a single API key per tenant. Existing API keys need a migration path -- default to "Default" workspace or grant access to all workspaces.
- **Cross-workspace lineage**: Dataset A in Workspace 1 may have lineage connections to Dataset B in Workspace 2. Does lineage traversal cross workspace boundaries?
- **Frontend routing**: Plan says `app.dataing.io/<org>/<workspace>/...`. Current frontend routing has no workspace segment. This is a significant frontend refactor.
- **Migration strategy**: Must decide: single migration or phased? Requires downtime? Recommend phased approach with "Default" workspace backfill first.
