# fn-33.3 Add verification API endpoint

## Description
## Add Verification API Endpoint

### What
Add `GET /api/v1/investigations/{investigation_id}/verify` endpoint that validates the integrity of an investigation's evidence hash chain.

### Why
The acceptance criteria require a verification endpoint that validates chain integrity. This is the primary interface for compliance auditors and automated checks.

### Approach

1. **Add response schema** in investigations route file or a new schemas module:
   ```python
   class ChainVerificationResponse(BaseModel):
       investigation_id: UUID
       is_valid: bool
       evidence_count: int
       root_hash: str | None
       root_hash_matches: bool | None  # does stored root_hash match computed?
       first_broken_seq: int | None
       error: str | None
       chain_available: bool  # false for pre-feature investigations
   ```

2. **Add route** on the investigations router (`entrypoints/api/routes/investigations.py`):
   - `GET /{investigation_id}/verify`
   - Auth: `Annotated[ApiKeyContext, Depends(verify_api_key)]`
   - Load investigation (check tenant ownership)
   - Load all evidence from `EvidenceRepository.get_evidence_by_run()` ordered by seq
   - If no evidence with chain fields: return `chain_available=false`
   - Call `verify_chain()` from `core/evidence.py` (fn-33.1)
   - Compare computed `root_hash` with stored `root_hash`
   - Return `ChainVerificationResponse`

3. **Handle edge cases**:
   - Investigation not found: 404
   - Investigation exists but no evidence: `chain_available=false, is_valid=true, evidence_count=0`
   - Pre-feature investigation (evidence without hashes): `chain_available=false`
   - In-progress investigation: verify what exists so far, note evidence may be incomplete
   - Cross-tenant access: blocked by existing auth middleware

4. **Regenerate frontend client** (`just generate-client`) since API schema changes
